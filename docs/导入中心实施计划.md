## 零、开工前置

三条已在设计文档定死、实施时不得再议的约束：

| # | 约束 | 违反后果 |
|---|---|---|
| B1 | **与提取的文本形态同源**：同一对编解码器（`a.Text` ↔ `SetText`）、同一路径语义（`manifest.Files[].path`）、同一类型来源（`manifest.Files[].dataType`）。`form=raw` 不在 v1 范围 | 文本侧本来就能往返；二进制侧规则见设计 §十一 |

另有两处需在写代码前实测确认（不确认就按保守处理）：

1. 提取产物 `pvf/` 下是否可能直接出现 `.lst`（种子本身是表、或某条边目标为表时）。**无论结论如何，P0 都拒绝把 `.lst` 当普通文件写**，所以这条只影响提示文案。
2. 常见归档里 `TypeUnicode` 条目的扩展名分布，用来评估 `dataType` 缺失时的推断准确率。

提取包解开后，`form=text` 的条目能按 `manifest.Files[].path` 回到归档；预览可编辑；不确认就什么都不发生。

### 1.4 执行序列（P0 版）

```
archiveTasks.begin()
  Lock → 校验令牌/TTL → ensureVersionReadyLocked → 记 repo/loadID/head
       → stage := CloneForBatch() → batchRevision++ → Unlock
  在 stage 上应用文件（带进度/取消）
  锁外 prepareArchiveDerivedIndexes(stage)
  Lock → 陈旧性二次校验 → after 快照（路径并集）→ 安装索引
       → recordVersionMutationLocked("导入中心") → MutationsSince/Clear
  Unlock → scheduleArchiveMutations → 三个事件
```

P0 的路径并集就是文件路径本身；P1 接上后扩展成 `files ∪ lst ∪ indexhash`。

### 2.4 顺序上的三个硬要求

1. **索引建在文件应用之后的 clone 上**（设计 D5）。实现上就是 `ApplyToClone` 里先落文件、再 `BuildListIndexes(a, specs)`、再判定。

## 七、已知缺口

- **indexhash 分支没有自动化测试**：`pvf.New()` 只能造标准（无 indexhash）归档，页格式档案造不出来。代码按规格实现并人工核对，但"表里有了行、客户端仍找不到"正是这条路径的故障形态，需要用 `PVF_TESTFILE` 指向 110 归档补一条集成测试。
- **三个页签没有运行时验证**：布局、虚拟滚动、原生目录对话框、执行后刷新编辑器，都只在类型层面通过。
- **二进制条目**（`form=raw`）按设计 v1 不导入；副本包里约 76% 是 `.ani`/`.til`，需要时按设计 §十一 接入。
