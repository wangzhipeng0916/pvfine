## 一、定位重构

### 1.1 pvfsimple 的形态从哪来

pvfsimple 工作在「pvfUtility 已导出的明文目录树」上，**没有归档索引**（`Dnf.cs` 8041 行无 `FileStream`/魔数/压缩逻辑，`.pvf` 只出现在"扫描时跳过"的 case 标签）。这个缺失直接决定了它的全部形态：

| pvfsimple 的做法 | 真实原因 |
|---|---|
| 8 个独立提取分区，每区一条专用链（副本/城镇/怪物/特效/APC/装备/礼包/宝珠） | 没有统一图模型，只能为每种内容手写一遍遍历 |
| 3 处 do-while 手工收敛（act 自引用、obj/mob/apc 联合增长、als↔ani 双计数） | 没有邻接表，只能靠"列表长度不再变化"判定收敛 |
| 4 处 `list.Clear()` 后重解析（`map_id.Clear()`、`Id_lst_路径查找` 末尾 `path.Clear()+AddRange`、宠物蛋扩展 ID 两处） | 迭代过程中就地改写共享列表的补丁式技巧 |
| `path[0]` 的扩展名决定整批解析规则 | 没有 per-node 类型，只能按批次假设同质 |
| `([\x20-\x7f]+\t){2}`/`{3}`/`{4}` 数制表符列数来判定 ID 属于哪个 registry | **列宽本身是格式真实语义**（见 §4.2 与附录 A.2），但它被硬编进正则、且没有 section 作用域限定，所以既脆弱又无法按版本调整 |
| 每次点击重新扫盘 | 没有持久化中间产物 |

⇒ **这些都不是需求，是约束的产物。照搬等于把别人的技术债移植过来。**

### 1.2 pvfine 的约束不同，因此结论应不同

pvfine 已有：常驻归档索引（715k 条目 / 577 ms 打开）、`ParseScriptView` 结构化 token 流（带 `SectionPath`/`TokenType`/`Index`）、`config/lists.json` 17 条 registry 声明（含 **contextual 路由**与 `union`）、SQLite 分片与增量索引框架、CAS 对象版本库、归档 diff、MOD writer、跳转标注引擎、Goja 沙箱。

⇒ **正确的设计**：把「引用边扫描」做成一个引擎，把「提取」做成它对子图的一次查询。**扫描有两种触发模式，默认是按需的**：

| 模式 | 触发 | 用途 | 是否阻塞提取 |
|---|---|---|---|
| **On-demand（默认）** | 用户点「提取」时，只对闭包实际触达的条目现扫 | 保证「载入归档 → 立即可提取」，行为等价 pvfsimple 的即时性，但无需先解包 | **否**。这是第一版的默认路径 |
| Eager（后台升级） | 打开归档后后台全量建图，或用户主动「建图」 | 让反向可达、影响面、覆盖率、孤儿检测从"做不到"变成一次索引查询 | 否，纯增量优化 |

两种模式共用同一个 `ScanFile` 实现与同一张持久化边表，差别只在**驱动范围**。所以"先扫全库才能提取"不是前提，而是可选项。

```
pvfine 载入 Script.pvf（core.archive）
        │
        ├─ 按需：闭包触达条目 ──► ScanFile ──► 边落表（增量）──► 前向闭包 ──► 落盘/report/.lst delta
        │
        └─ 后台：全量 ScanArchive ─► 完整引用图（持久化）◄─ 增量维护（复用现有 delta 索引模式）
                                        │  查询
              ┌──────────┬──────────────┼──────────────┬──────────────┐
              ▼          ▼              ▼              ▼              ▼
          反向可达     最小集       孤儿/未引用     影响面        跨版本图 diff
         （谁引用我）（MOD 精简）  （死内容检测） （改 .ani 崩哪）（配 pvfsimple 无）
```

**"提取中心"这个 UI 名字保留**，但它是「前向闭包 + 落盘」这一个视图；其余视图共用同一份数据与同一个扫描引擎。这样 v1 的交付量没有膨胀，后续能力也不再需要第二次架构改动。

**交付形态（明确一句话）**：pvfine 内、载入 `Script.pvf` 后、直接从当前归档提取 —— **不需要 pvfUtility，不需要事先解包成明文目录，不需要外部 HTTP 桥**（这三条都是 pvfsimple 的硬前提，我们已在 §1.1 消除）。提取是**只读操作**，不修改归档；写回归档走已有的 `SaveAs`/VCS 通路。

## 三、真实 86 数据的实测结论（不变的部分）

**规模**：715,537 条目 / 577 ms。顶层目录 equipment 209,686、monster 178,959、passiveobject 130,680、map 67,595、stackable 46,847、character 29,431、aicharacter 19,727、n_quest 7,808、creature 6,483、skill 2,918、npc 2,222、dungeon 1,905、appendage 1,120、town 82、region 27。

**扩展名**：`.ani` 316,870、`.equ` 145,449、`.act` 65,398、`.stk` 42,496、`.obj` 18,990、`.ai` 18,966、`.til` 18,386、`.atk` 16,416、`.map` 14,475、`.key` 12,570、`.ptl` 10,623、`.als` 8,457、`.qst` 7,799、`.mob` 5,705、`.skl` 3,028、`.dgn` 1,398、`.aic` 1,140、`.etc` 1,109、`.apd` 1,079、`.cre` 552、**`.tbl` 111**。dataType：脚本流(1) 714,270 / UTF-16(3) 1,267。

**registry**：103 个 `.lst`。`equipment.lst` 119,531 行、`stackable.lst` 43,034、`passiveobject.lst` 18,201、`map.lst` 10,292、`monster.lst` 5,064、`quest.lst` 3,442、`dungeon.lst` 1,046、`etc/equipmentpartset.etc` 29,003 行。单文件解码成本：1.2 MB → read 7.5 ms + decode 51 ms。

**四条直接改变设计的结论**

1. **86 是旧式 `<dir>/<dir>.lst` 布局**（`dungeon/dungeon.lst=true`、`list/dungeon.lst=false`）；17 条 relation 全命中，`FindList` 双布局探测正好覆盖。
2. **pvfsimple 的正则对应 60 版，不是 86 版。** 它搜的 `[ANI FILE]`/`[file name]`/`[SUMMON APC]`/`[CREATE PASSIVEOBJECT CIRCLE]`/`[equipment part set]`/`[aurora graphic effects]` 在 86 的 `.act`/`.equ` 采样中**零命中**；86 实际是 `[MOTION]`+`[BASE ANI]`(119/119)/`[SUB ANI]`(53)/`[INDEX]`(28)/`[CREATE PASSIVEOBJECT]`(27)/`[SUMMON MONSTER]`(2)/`[RANDOM SELECT]`(4)。
   ⇒ **这正是知识库 `monster-ai-action-attack-cross-layer` / `client-compatibility-matrix` 描述的版本漂移。移植正则必然错，必须按目标版本重新确定边集。**
3. **registry 路径是「列表目录相对 + 大小写混杂」**：`monster.lst` → `1\t`Goblin/Goblin.mob`` ↔ 索引 `monster/Goblin/Goblin.mob`；`dungeon.lst` → `Act1/Grakkarak.dgn` ↔ `dungeon/act1/grakkarak.dgn`。⇒ 归一化固定为「全小写 + 正斜杠 + `path.Join(listDir,row)` + 大小写不敏感 `Find`」。
4. **`.img` 不在归档内**（扩展名直方图无 img），归档里只有指向客户端资产的引用：`[icon] = `item/new_equipment/08_necklace/necklace.img` 69`、`[field image] = `Item/FieldImage.img` 6`、`[icon animation] = `anicon_7th_birthday.ani` 1`。⇒ 节点必须区分 `Entry` 与 `Asset` 两类；资产缺失不算失败（知识库口径「PVF 引用存在 ≠ 客户端资源存在」）。

其它已验证：`.ani` 在 86 是文本（`[LOOP]/[FRAME MAX]/[FRAME000]/[IMAGE]/[IMAGE POS]/[DELAY]`）；owner-relative 真实存在（`proc.act` → `` `../animation/proc.ani` ``，`.map` → `` `Tile/Tile01.til` ``）；`.ptl` 承载引用（`[object type]` 53/121、`[object]` 53）—— **印证 pvfsimple `Dnf.cs:944 case "ptl"` 死分支本该提取却从未执行**；`[stackable type]` 实测 14 种（`usable cera package` 340、`booster` 241、`upgradable legacy` 106、`booster selection` 60、`etc` 57、`waste` 21、`enchant waste` 20、`cera booster` 17、`material` 17、`town and dungeon` 6、`cera package` 5、`expert town potion` 5、`dye` 2、`upgrade limit cube` 1），pvfsimple 覆盖其中 7 种；`skill/atpriestskill.lst` 在 `lists.json` 已声明但 86 不存在 ⇒ contextual 路由必须容忍按版本缺失；字符串占位符有两形（`<31::equip_name_1>` 可解，86 实际的 `<DNF7周年盛世庆典>` 不可解）⇒ 现有 `exportPlaceholders` 在 86 上会漏。

## 四、核心模型

### 4.1 节点必须按 registry 命名空间隔离，绝不能是裸整数

这是从知识库里读出来、且 pvfsimple 踩了坑的一条：`pvf-registry-lst-topology-fields` 明确「数字 ID 无全局唯一语义」，6255 个 ID 跨 registry 重复。

pvfsimple 的具体失配点：`Stk宝珠寻找卡片Id`（`Dnf.cs:5823`）把卡片 ID 追加进调用方传入的同一个 ID 列表，随后**用这个混装列表再查 `stackable.lst`**；`Equ宠物蛋寻找宠物Equ`（`:5447`）同样把下层 equ ID 追加进 `equ_id` 自身再整体清空重解析。数值撞号时会静默解析到错误条目。

⇒ 图节点定义：

```go
type NodeKind uint8
const (
    NodeEntry    NodeKind = iota // 归档内条目，键 = FileIdentity
    NodeRegistryRow              // 某 .lst 的一行，键 = (registry名, ID) —— 命名空间隔离
    NodeAsset                    // 客户端 .img（归档外），键 = 归一化 img 路径
    NodeStringTable              // <table::key> 文字表
    NodeUnresolved               // registry 有行但条目不存在
    NodeUnmodeled                // 疑似引用但边目录未声明（可查询、可统计）
)

type NodeID struct {
    Kind NodeKind
    Key  string // FileIdentity / "monster:12345" / "sprite/.../x.img" / "str:31:key"
}
```

`NodeRegistryRow` 与 `NodeEntry` 是两个节点，中间用一条 `registered-as` 边连接。这样"注册了但文件不存在"在图上是可见的（`registered-as` 指向 `NodeUnresolved`），而不是像 pvfsimple 那样靠最后 `File.Exists` 兜掉。

### 4.2 边：声明式，复用已有 schema 而不是发明新 schema

```go
// internal/extraction/edges/extract-edges.json —— 与 lists.json 同机制 //go:embed
type Edge struct {
    ID            string    // "map.passiveObject"、"act.motion.baseAni"…
    From          Match     // {extensions:[…], pathPrefix:[…]}
    Section       string    // ScriptElement.Section（不含方括号）
    SectionPrefix []string  // SectionPath 前缀，如 ["motion"] → 精确区分 [MOTION] 内/外的 [INDEX]
    TokenTypes    []int32   // 6=反引号路径，0=整数 ID，2=浮点
    Record        *Record   // ★ 记录形状，见下（实测必需，不能省）
    Target        Target    // {kind: entry|registry|asset|string, relation:"怪物", ownerRelative:true, fallback:"(r)"}
    Context       *Ctx      // 上下文路由：直接复用 RelationSpec 的 contextual/contextPaths
    Versions      []string  // 生效 PVF 版本（沿用 annotations.Rule.PVFVersions 同一模式）
}

// Record 描述一个 section 内的扁平 token 流如何切成记录。
type Record struct {
    Width      int          // 0=每个 token 都是引用；N=定宽记录
    IDOffsets  []int        // 定宽记录里哪些列是引用
    KindColumn int          // 变宽记录：该列的 t=6 标签决定 registry
    KindRoutes map[string]string // "[item]"→"物品"、"[trap]"→"被动对象"…
}
```

**★ 实测修正（v2.1）**：我在初稿里断言「`SectionPath` + `Context` 让 pvfsimple 的列宽猜测被彻底删除」——**这条错了，实测推翻它**。`ParseScriptView` 把一个 section 内的所有值**扁平化**成一个 `Index` 序列，行边界丢失。真实数据（86）：

| Section | 实测记录形状 | 引用列 |
|---|---|---|
| `.map [passive object]` | 定宽 **4** | 列 0 = 被动对象 ID |
| `.map [monster]` | 定宽 **10**（`ID,x,y,?,?,?,1,1,[fixed],[normal]`） | 列 0 = 怪物 ID |
| `.map [animation]` | 定宽 **5** | 列 0 = `.ani` 路径 |
| `.dgn [map specification]` | 定宽 **4**（`"map",x,y,mapID`） | 列 3 = map ID |
| `.twn [area]` | 定宽 **3**（`idx, "X/…map", "[gate]"`） | 列 1 = map 路径 |
| `.map [special passive object]` | **变宽**，列 5 是类型标签：`ID,x,y,?,1,[item],0,1,-1,-1,-1` | 列 0，registry 由列 5 的标签决定 |
| `.dgn [pathgate object]` / `.aic [ai pattern]` / `.map [tile]` / `.mob [waiting motion]` | 宽度 1，每列都是引用 | `Record.Width=0` |

⇒ 所以 **pvfsimple 的"数制表符列宽"不是技术债，而是它在如实表达格式的语义**。区别只在于：它把列宽硬编在 60 条正则里，我们把它做成 `Record` 数据 + 由 `SectionPath` 限定作用域（这一半的收益是真的：`.map [event monster position]` 的坐标是纯整数，靠 `Section` 限定就能排除，靠全局正则则必然误收）。

**实现要求（新增）**：变宽记录必须按**行**分组解析，不能按扁平 `Index` 取模。`ScriptElement.Start/End` 是 UTF-16 码元偏移，可用 `strings.Count(text[:Start], "\n")` 反推行号后再切记录 —— 这是 `ParseScriptView` 之上必须自建的一个原语（或改用 `ParseScriptDocument`，它保留 section 树结构）。

边目录与 `annotations.json` 的 reference/path 规则**成对维护**：加一条边就顺手补一条编辑器跳转规则（项目已有 `pvf-json-rules` skill 覆盖该编辑流程）。两者共用同一份 `RelationSpec`、同一个 `ParseScriptView`，但语义分工不同（边要展开多行/成组 ID/带版本区间，标注只需高亮首个），故按已定决策**独立成文件**。

### 4.3 三态是一等公民，不是日志文本

pvfsimple 最严重的问题是**静默欠提取**且无法自知。已确证 6 类丢数据：`case "ptl"` 死分支、`"plt"` 拼写错误（`Dnf.cs` skl 引出的 `.ptl` 全丢）、`Groups[2]` 组序依赖、`%d%d.img` 只展开 01–09、`...\` 根相对引用被 `continue` 丢弃、三条链把 `root\monster\` 当 pvfDir 导致拼出 `monster\monster\...` 畸形路径后被 `File.Exists` 静默兜掉。

⇒ 每条边的解析结果必带状态，且状态**进图、可查询、可统计成覆盖率指标**：

- `Resolved` / `Missing`（registry 有行、条目无）/ `Unmodeled`（引用形态成立但无声明边）/ `Unknown-asset`（动态路径未展开，按知识库规定**不得降格为 missing**）
- **边目录覆盖率** = `Resolved / (Resolved + Missing + Unmodeled)`，作为回归指标写进测试。这是 pvfsimple 完全没有的自度量能力。

### 4.4 遍历语义只有三种，不要全部改成不动点循环

按已确认的算法规格，pvfsimple 里真正的收敛循环只有 3 处（act 自引用、obj/mob/apc 联合增长、als↔ani 双计数），其余都是固定层数：`[import script]` 固定 2 层、`寻找ai` 固定 1 层、`Id_lst_路径查找` 单层反查。

⇒ 图上统一表达为 `Traversal{Direction: forward|reverse, EdgeFilter, Depth: unlimited|N, Mode: closure|bounded}`。深度上限即固定层数；`Mode=closure` 即不动点。**不再需要"删除自己/删除对方"技巧**——它们是为了在共享列表上模拟深度上限和反查回写，图模型里是 `Depth` 与 `Direction` 两个参数。

## 六、存储与性能（已实测，见附录 A）

**实测结论（2026-10-16，`Script.pvf` SHA `7bfeab46…`，附录 A）：性能不是本设计的约束。**

- **冷启动闭包一个真实副本**（`dungeon/act1/grakkarak.dgn`，registry 完全不预热）：**131 条目 / 29 ms**，其中含 3 个 registry 的懒加载 11 ms。每条目均摊 **0.218 ms**。
- 外推：1 万条目级闭包 ≈ **2.2 s 单线程**；若并发扫描可再降。⇒ 「载入封包后即可提取」成立，且体感远好于 v2 的"秒级"估计。
- **9 个 registry 全量解析 = 169 ms**（被动对象 18,202 行 / map 10,293 / 任务 3,443 / 怪物 5,065 / APC 1,022 …）。即 eager 预热 registry 几乎免费；贵的只是全库 71 万条目的正文扫描。
- 解析质量：278 个引用候选 → **271 resolved / 0 路径缺失 / 6 registry 未解析**（97.5%）。owner-relative + 根相对 + `(r)` 三级回退在真实数据上零路径失配。

**全量建表成本：已实测（阶段 1，见第十二节）= 715,537 条目 / 3m19.5s / 3586 条目每秒 / 落盘 335 MB**，落在下表"1–10 min"档 ⇒ **eager 一律手动触发 + 分片**，不作为默认。按顶层目录分片可并行到 4 核以内，单片（如 `.ani` 31.6 万）约 88 s。

| 全量扫描实测 | eager 策略 |
|---|---|
| ≤ 60 s | 打开归档即后台自动预建 + 增量维护（E10），UI 显示建图进度 |
| **3m19s（实测落点）** | **手动触发 + 按顶层目录分片**（equipment/monster/passiveobject/map 四大头占 56 万），照 `advanced_search_shards.go` |
| > 10 min | eager 仅作可选项；反向/覆盖率类功能标注为"需先建图"，前向提取仍全程 on-demand 不受影响 |

建表后同一个副本种子：**建表闭包 9.1 ms vs 实时闭包 53.6 ms（5.9x）**，且**条目集合与覆盖率完全一致**（0.8879）。

两种模式都受益的一条优化：**只扫"含已声明引用位 Section"的条目**（先用边目录的 Section 集合做一次粗筛），可把扫描量砍掉一大截，且不影响正确性 —— 未声明的引用位本来就要标 `Unmodeled`，粗筛用的是同一份目录。

存储：`edges(src_identity, dst_key, edge_id, state, ctx)` 落 SQLite（复用现有索引目录与 `sqlite_rebuild` 生命周期），主键用 `FileIdentity` 而非 int 索引以防编辑后漂移。表是**增量填充**的：on-demand 扫到哪就写哪，eager 只是把它填满。闭包查询在 SQLite 里是一条 recursive CTE，或载入内存邻接表后 BFS——两种都由同一份数据支撑，先按实测择一。

## 十、为什么这个设计优于"照 pvfsimple 移植"（一句话汇总）

1. 它的 8 条链来自**没有索引**这个约束，而 pvfine 有索引 → 收敛成 1 个 preset 声明表。
2. 它的 3 处 do-while + 4 处 `list.Clear()` 来自**没有图**这个约束 → 收敛成 `Traversal{Direction,Depth,Mode}` 三个参数。
3. 它的列宽正则 `(\t){N}` —— 实测证明**列宽是 PVF 的真实格式语义，不能消除**（附录 A.2）。被消除的是另外两样：把列宽硬编在正则里（改为 `Record` 数据 + 可按版本覆盖），以及没有 section 作用域限定（改为 `SectionPath` 约束，从而能排除 `[event monster position]` 这类纯坐标整数）。
4. 它每次点击重扫盘 → pvfine 有分片/增量索引范式，一次建图反复查。
5. 它**不知道自己漏了什么** → pvfine 把漏的部分做成可查询的 `Unmodeled` 队列，还能自动建议边声明；补边从"人肉比对界面按钮"变成"看覆盖率下降"。
6. 它的 3844 行职业×layer 硬表随版本失配 → 扫 `jumpattack.ani` 的算法 + 例外覆盖。
7. 它只能前向 → 反向/影响面/MOD 最小集/死内容检测/跨版本图 diff 全部免费，且这些恰好接上 pvfine 已有的 `internal/mod`、VCS、`ArchiveDiffService`。
8. 它的输出是"一堆文件 + txt" → 改为带 `pvfSha256`/`edgeSetHash` 的可复现 manifest + 可审阅的 registry delta。

### 阶段 1 实施记录（2026-10-16 完成，持久层后于 2026-10-17 退役）

新增 `internal/extraction/store.go`（持久化引用图）、`discover.go`（边建议引擎）与 `store_test.go`，边目录扩到 **59 条**，`cmd/edge-bench` 增加 `-store` / `-suggest` / `-reverse` 能力。

**后记（任务 #15，2026-10-17）**：该持久层随后被用户否决（"我觉得这个东西不需要数据库"），且实测确认它**没有消费者**——产品主路径（按需闭包 + 直接落盘）不读它，`cmd/extract` 也不读它。本轮把 `store.go`/`store_test.go` 与 `edge-bench -store` 撤下（源码移到仓库外 `E:\00\extraction-rejected\`），并把边建议引擎改绑到内存缺口队列，使 `-suggest` 在不持久化的前提下仍然可用。下面两条 SQLite 使用要点**作为事实保留**：它们是本仓库 SQLite 管线的真实约束，将来若按 §14.1 的正确身份范式重启，仍然适用。

**一个必须纠正的设计前提**：`pvf.FileIdentity` 是**进程内自增计数器**（`archive.go:39 nextFileIdentity atomic.Uint64`），重开归档即全部变化。§4.1/§六 原写"持久层主键用 FileIdentity"是错的——它在单次会话内防索引漂移是对的，跨重启无意义。改为沿用本项目既有约定：**行按 `file_index` 定键，整个库绑定一个归档身份摘要**（源路径 + size + mtime + FileCount + Header.GroupCount/BodySize + TextEncoding + SavedContentHash），摘要不符时 `OpenStore` 直接返回 `ErrStoreBusy` 而不是静默复用。缓存文件名内嵌摘要前 16 位，与 `services/sqlite_index.go` 的 `archiveIndexIdentity` 同一思路。

**实测发现的关键 bug（本项目最贵的一条）**：`plausibleExtension` 原本要求扩展名**恰好 3 个字母**，而 PVF 存在 `.ai`（精灵定义，2 字母）与 `.h`（1 字母）。该规则会**永久静默丢弃全部 `.ai` 引用**。真实 86 单副本测试**没有暴露它**——`Act1/GrakKarak` 恰好不含 APC/怪物分档 AI；是合成 fixture 暴露的。其全库足迹实测为：`.mob [normal]/[expert]/[king]/[master]` 各约 17,669 次 + `[slayer]`，合计 **≈8.8 万条引用**。⇒ 结论写进规约：**只跑真实归档测试不够，必须同时保留可精确构造边界的小型合成归档测试**。

**两个 SQLite 使用要点**：
1. `Build` 在开写事务**之前**用同一个 `*sql.DB` 读 `scanned` 集合，会被连接池派到第二条连接，与随后的写事务冲突并报 `SQLITE_BUSY (WAL)`。改为在事务内读（`scannedSetTx`）。
2. 边表主键 `(src, edge_id, value, dst)` 天然去重，导致**建表闭包的覆盖率与实时闭包不一致**（4.31M 次引用塌缩成 828K 条不同边）。补 `occ` 列累加出现次数后，两个视图的条目集合与覆盖率完全一致（0.8779→0.8879 全等）。⇒ 图与日志是两种语义，选去重就必须把次数显式存回来。

**全量建表实测**：715,537 条目 / **3m19.5s** / 3586 条目每秒 / **335 MB**；引用出现 4.31M 次、去重后不同边 828,200 条、缺口类 2749（路径型 494 + 数值型 2255）。建表后同一副本种子闭包 **9.1 ms vs 实时 53.6 ms（5.9x）**，结果完全一致。反向依赖已在真实数据上工作：`destparticle9.ani ← 2 个 .ptl（经由 ptl.object）`。

**建议引擎按证据分三级**，并明确拒绝两类推断：`path`（反引号路径，形状即证据）、`reused-section`（同名 section 已在别的扩展名上声明为引用，可继承目标）、`manual`（无佐证的数值缺口，永不自动生成边）。空 section 的缺口（如 `.etc` 根级条目）被显式拒绝，因为它无法构成合法边声明。输出为可直接并入 `edges/extract-edges.json` 的 JSON，且测试断言"合并后必须通过 `NewCatalog` 校验"。

**撤回我先前的一条建议**：原计划把"数值型缺口改成 registry 归属判定"。实测数据否定了它——`delay`/`weight`/`cast speed`/`gravity` 这类值大量存在于 11 万行的 registry 里，任何成员测试都会误报，而真引用（`.mob [item]`=1001）与普通数值无法用静态规则区分。因此改为**同 section 佐证**（只有当该 section 名已在别处被声明为 registry 引用时才继承），其余一律留给人/Agent 判断。

**闭环工作方式已复现两轮**：全库队列 → 补 `dgn.difficultyTables`/`dgn.revisionTable`/`map.tileFiles`/`mob.attackAction`/`mob.aiByLevel*`/`equ.aniScript` 等边 → 该副本路径缺口重新归零。

**新增边的副作用已可见而非隐藏**：加入 `.mob` 分档 AI 边后，`missing` 从 6 涨到 86。这些是"引用存在但目标文件不存在"的条目，属预期（并非每个怪物都有全难度专用 AI），但必须逐段复核以确认不是记录宽度误判。

### 13.3 P1 记录模型替换：`lines.go` 已删除，改为计数前缀自同步（2026-10-16）

**起因**：判据 2 早已指出 `[special passive object]` 的宽度在 rendering 里没有规则，行分组实际建立在渲染器默认宽度之上；而实测发现更严重——该边没声明 `width`，`positionAllowed` 直接放行**全部**整数 token，于是记录里的坐标与载荷参数都被当成引用，且用"该行第一个 kind 标签"给同一行所有值路由。

**实测出的真实形状（86 全量，14475 个 `.map` 中 5467 个含本段）**

```
记录 = ID x y z n <item>×n        n 在第 5 列（0 基），即"条目数"
普通条目 = kind + 5 列载荷（末列 -1 填充），共 6 列
         例：222 1170 204 0 1 `[trap]` 2011 1 1 3 -1
         例：18162 1169 177 0 1 `[item]` 0 1 -1 -1 -1
配对条目 = `[hellparty]` … `[/hellparty]`，内部是 `ID 概率 档位` 三元组
```

⇒ **记录可以自同步**：计数列 + 条目宽度就能切出边界，**不需要源码行、不需要渲染规则**。新形状声明为 `record.countPrefixed{prefixTokens, countIndex, itemTokens, kindIndex, nestedKinds}`，`Record.lineGrouped / kindColumn / kindRoutes` 与 `lines.go`、`LineIndex` 一并删除。

**验证（全库精确消费判据，已固化为门控测试 `TestCountPrefixedConsumesRealMapsExactly`）**

| 指标 | 结果 |
|---|---|
| 含该段的 `.map` | 5467 |
| **精确消费（走完 section 最后一个 token，无剩余无越界）** | **5467 / 5467** |
| 切出记录数 | 18,012 |
| `record-malformed` 报告 | 0 |
| 变异判据（把计数列指向 kind 标签） | 基线 46 引用 → 变异后 44 引用 + **1 条 malformed**，即错位必须可见 |

**行为变化（同一组 6 种子）**：闭包 283 → **249** 条目，`resolved` 1093 → 962，`map.specialPassiveObject` 命中 32 → **5**（2 个 map 里真正的记录数），`.obj` 30 → 17、`.ani` 180 → 160。判据 1 仍是 **0 违反 / 0 漏边**，判据 3 仍是 **0 不一致**。

**必须如实说明的取舍**：旧实现"多出来"的引用里，一部分是坐标/载荷之类的**假引用**（`"1"` 命中 `particlefactory/forgesmoke.obj` 这种），另一部分可能是**真引用**——例如 `[trap]` 载荷 `2011` 解析到 `hpfairy.obj`，语义上像是"这个陷阱会生成该对象"。新实现只认记录首列，这些载荷值**进入候选队列**（`payload[trap]` / `payload[monster]` / `payload[item]`，dungeon 单副本 18 条）而不是丢进闭包。下一步应按 **kind × 槽位**实测命中率，再决定把哪个槽位声明为引用——这正是"检测要宽松、声明要严格"的应用。

**顺带收益**：计数前缀记录是**扁平**的，因此可以用合成 fixture 覆盖（行分组时代做不到，因为归档写入器会把 section 体压平成一行），`TestCountPrefixedRecordBoundaries` / `TestCountPrefixedNestedBlockSkipsPayload` 两条 fixture 测试补上了这块空白。

**P1 收尾两项（同日完成）**

**① 覆盖率换成非自指指标。** 旧 `Coverage` 保留但标注为自指（分子分母都来自扫描器自己的判定，换记账方式就能变），新增 **`VocabCoverage` = 被已声明边消费的文本 token / 被扫描条目里的全部文本 token**。分母是归档自己的内容，任何能反编译同一批条目的人都能复算。同一组 6 种子实测：**0.5496（908/1652）**，而自指的旧指标是 0.8481 —— 差额 744 个未被消费的文本 token 才是真实的补边工作队列。

**② 判据 2 升级为 lint 断言**（`width_lint_test.go`）：边目录声明的每条宽度要么与 rendering 对同一 section 的规则**一致**，要么登记进 `widthDeclarationWhitelist`（每条带实测依据）。当前结论：**冲突 0 / 未登记 0 / 仅渲染侧 0，白名单 12 条**。白名单自身也受检——条目一旦不再是不受交叉验证的声明（rendering 补了规则或边被删）就会报错，防止它悄悄掩盖新问题。

### 13.4 P2 读取路径与并发：token 流直读（2026-10-16）

**做法**：新增 `Archive.ScriptViewOf(index)` —— 直接解码归档自己的 5 字节 token 流并复用与文本解析器**同一套**节算法（`elementsFromLexemes`），不再走「`Text()` 全量反编译 → `ParseScriptView` 重新词法」的双重解码。ACT60 与 `TypeUnicode` 条目自动回落到文本路径，调用方看到的语义不变。只给 `internal/pvf` 加了只读入口（G2 已授权），未改既有行为。

**等价性（门控测试 `TestTokenStreamViewMatchesTextPath`，`PVF_EQUIV_SAMPLE` 可调深度）**

```
全库 357,136 个 TypeScript 条目：结构不一致 0
其中 23 个仅在「无效 UTF-8 字节」上不同：token 路径保留原始字节，文本路径经 []rune 变成 U+FFFD
```

那 23 个是**已登记且更正确**的差异：都是 `[name]` 里的韩服残留字节（如 `Caf\xa8\xa6 Server White Coat`）。保留原始字节才可能匹配归档条目，替换字符永远匹配不上；两条路径对"该值是否构成引用"的判定完全一致，所以图不变。

**性能（同一归档，715,537 条目）**

| 指标 | 旧路径基线 | 现在 |
|---|---|---|
| 全扫吞吐 | 3,586 条目/s（199.5 s） | **28,615 条目/s（25.0 s，单线程）** |
| 全扫吞吐（20 并发） | — | **56,478 条目/s（12.67 s）** |
| 单副本闭包 | 91 ms | **17 ms**（预热后） |
| 六种子闭包 | 859 ms | **23 ms**（预热后）；导出 1.5 s → 0.34 s |

### 13.7 产物形态定为「文本」：与源码导入的两种模式一一对应（2026-10-17）

**用户指出的问题**：提取产物不该是二进制形态，应当与本应用「源码导入」支持的内容解析方式对应——即不带 `.txt` 后缀的文本。原先我把"原字节"当默认、把文本做成 `.txt` 副本，是自作主张。

**实测支撑（86 全量抽样）**

| 事实 | 数据 |
|---|---|
| 闭包内条目几乎全是脚本 | 抽样 1,497 条中 **`.ani` 663 条也是 script**；仅 3 条 `.xui` 是未知类型 3，无二进制 |
| 文本往返的**语义**一致性 | **1497/1497 逐元素一致**（Kind/TokenType/Value/Section/SectionID/Index 全同） |
| 文本往返的**字节**一致性 | 1319/1497（88%）；差异全在 **kind=6 字符串的池偏移被重编号**，文本一字不差 |

⇒ 文本形态是**语义无损**的；字节差异只是池槽位，不构成信息丢失。因此判据 3 不能再用"逐字节一致"来度量文本形态。

**落地**

- `Selection.Form`（并 `ExportOptions.Form`）默认 **`text`**：把反编译文本写到**原路径原名**（`pvf/monster/goblin/goblin.mob` 内容是文本，无 `.txt`），与导入的 `text` 模式对应；`raw` 保留原字节，与导入的 `raw` 模式对应。CLI `-form text|raw`，服务层 `ExtractionRequest.Form`。
- 无文本形态或反编译失败的条目**自动写原字节**，并在 manifest 逐文件记 `form` 与 `counts.textFiles/rawFiles`——降级可见，不静默。
- **判据 3 改为形态感知**：raw 条目逐字节比对；text 条目校验 **UTF-8 合法**（导入的文本模式会拒收非 UTF-8）+ **重新解析后与归档条目的 ScriptView 逐元素一致**。实测：`-form text` 208 条文本 0 不一致；`-form raw` 208 条原字节 0 不一致。
- 新增门控测试 `TestTextExportIsImportableAndFaithful`：默认形态即文本、产物是合法 UTF-8、解析后与归档语义一致；raw 形态逐字节一致。
- 一条实现教训：写出形态的判定必须在**写出器与校验器之间共用同一函数**（`EffectiveForm`）——最初校验器按"条目有没有文本能力"判断，于是 `-form raw` 时把原字节当文本校验，报了 208 条假失败。

### 13.8 登记表片段：把"涉及到的登记行"随产物带走（2026-10-17）

**用户指出的缺口**：产物里**应该有 `.lst`**。核对后确认：`.lst` 不在闭包里（没有任何边指向它们），所以此前产物里一行都没有。用户同时明确范围：**不是整张表，也不是只列未登记的**，而是"提取内容涉及到的"登记行——并指明参照反编译工具的做法。

**参照实现**：pvfsimple 的 `Id_lst_编号查找` 按 ID 去 `.lst` 查行，收集 `id<TAB>`路径`` 形式，输出成按表分块的「以下内容加入PVF【monster/monster.lst】文件内」。即：**已登记的命中行**；未登记的自然查不到（它还额外输出应当补登记的内容）。

**为什么不带整张表**（86 实测，这就是答案的关键）：

| relation | 登记表 | 整表字节 |
|---|---|---|
| 装备 | equipment/equipment.lst | 1,195,320 |
| 道具 | stackable/stackable.lst | 430,350 |
| 被动对象 | passiveobject/passiveobject.lst | 182,020 |
| map | map/map.lst | 102,930 |
| 怪物 | monster/monster.lst | 50,650 |
| 其余 10 张 | dungeon/town/region/npc/quest/apd/creature/itemshop/worldmap/character | 合计 ≈ 40,000 |

整表合计 ≈ **1.94 MiB**，而一次副本产物只有 0.19 MiB。且 `.lst` 必须整张才合法（截成片段导入会破坏 registry），所以"要不要整表"只有全有/全无两态。

**落地形态**：`_registries/<表名>.lst.fragment`，内容是**该表被本次提取用到的行**，保持表里原样拼写、按数值排序，可直接追加；未登记的 ID 在同一文件里以 `# ` 注释行标出（不伪装成行）。实测一次副本（+怪物）产物：4 个片段共 **1.2 KB**（map 54 B / monster 170 B / passiveobject 865 B / stackable 95 B），全表则是 1.94 MB —— 相差约 1600 倍，而信息量正是"内容涉及到的"那部分。

**实现要点（一处值得记的坑）**：片段必须**重扫导出集**、而不是遍历 `closure.Edges`——闭包只保留可跟随的边，未登记的 ID 正是最该出现在这份产物里的东西，走闭包会让它整块消失。判定"缺行"依据**表**而非引用状态：已登记但目标文件缺失的 ID 依然在表里有行，就该作为行出现。

**默认产出**（`-no-fragments` 可关；服务层同）。86 实测 **0 张表有 `_indexhash.etc` 伴随文件**，故本归档无额外负担；伴随机制存在于其他客户端，若出现应随表一起带。manifest 记 `selection.registryFragments`（含 relation/listPath/行数/缺行数）与 `counts.registryFragments`。

### 13.10 派生缓存失效：预览绑定内容而不是指针（2026-10-17，任务 #22）

**问题**：预览槽有 10 分钟 TTL，此前"是否仍有效"只看归档指针。就地编辑（`SetText`/`SetRawBytes` 写 overlay）既不换指针也不换 `archiveGeneration`，于是旧预览照样能落盘——落的是**改后**的字节，而用户确认的是**改前**的清单与计数。扫描器缓存同一毛病更狠：`.lst` 改了它仍用旧行解析。

**为什么不能直接用 `MutationCheckpoint`**：变更日志是**会被别人吃掉的临时量**——`scheduleArchiveMutations` / autosave / version / search_index 等 20+ 处调用后会 `ClearMutations()`；`Save()` 又把 overlay 清空（`internal/pvf/save.go:604`）。守卫 `watch_test.go` 把这条钉成断言：编辑并保存后 `MutationCheckpoint()==0` 且 `len(PendingEdits())==0`（两个廉价信号同时哑火），而内容指纹仍然变了。仓库里没有跨 journal 重置的单调修订量，所以只能自己取证。

**方案：三层缓存键 + 内容指纹**

| 层 | 键 | 覆盖的变化 |
|---|---|---|
| 预览（`extractionPlan`） | 归档指针 + `archiveGeneration` + `Watch` | 换包/结构增删、就地编辑、编辑后保存 |
| 扫描器（`ExtractionService`） | 归档指针 + `archiveGeneration` + `Watch(登记表)` + `*annotations.Engine` | 换包、`.lst` 内容、规则覆盖 |
| 导出用表 | `plan.scanner`（随预览冻结，不再取实时 scanner） | 预览与落盘用的是同一份关系表 |

`extraction.WatchEntries(a, indexes)`（新文件 `internal/extraction/watch.go`）把 `FileCount` 打头，再按**索引去重升序**写 `(FileIdentity, len(path), path, len(payload), payload)` 进 FNV-1a/64。`Watch` 是可比较结构体，判过期就是 `==`。指纹集合 = **闭包全部节点** ∪ **所有登记表**：前者因为任何一个条目改内容都可能增减它的出边；后者因为改一行会重新解析一批 ID，而它既不动 generation 也不动条目数。`RegistrySet.ListFiles()` 负责枚举——声明表、contextual 全部备选路径、union 展开后的具体表，去重排序，且用 relation 级 visited 集合挡住自引用 union 的死循环。

**规则覆盖怎么进来**：提取用的 relation 表由本服务从 `ruleStore` 取合并后文档（§13.6 的委托方向不变），而规则变更的唯一入口是 `RuleService.activate` → 替换 `c.annotationEngine`（`ForVersion` 已 scoped 时返回同指针，故"指针没变"就等价于"文档没变"）。把引擎实例身份并进扫描器缓存键，等价于搜索索引在规则重载时比 `searchIndexSpecFingerprint` 的既有做法，不需要新增事件或改共享文件。

**实测成本（86 版 `Script.pvf`，`PVF_TESTFILE`）**

```
预热（basename 索引 + 31 张声明表）        547 ms（不变）
登记表指纹  30 条目 / 2.07 MB               3 ms   ← 每次 Prepare 的缓存键检查
闭包指纹    223 条目 / 2.28 MB              2 ms   ← Prepare 取证 + Execute 复核
闭包 12 ms / 导出 705 ms / 判据 1-5 全绿（遍历违反 0、漏边 0、文本不一致 0）
```

即指纹把 Prepare 从 ~12 ms 抬到 ~15 ms，比它保护的那次扫描更便宜；条目上万、上百 MB 的整档导出会到百毫秒量级，而那条路径本来就要把这些字节读一遍。

**测试**：`internal/extraction/watch_test.go` 4 条（顺序无关 / 只对被 watch 的条目敏感 / **journal+overlay 双双清空后仍敏感** / 条目数变化也敏感）；`services/extraction_test.go` 新增 2 条（编辑并保存后 `Execute` 必须 `ErrExtractionStale`，重新 `Prepare` 后可执行；删掉一行登记后旧预览作废且新预览闭包 3→1，证明登记表真的重读了）。

**诚实边界**：指纹只覆盖参与本次预览的条目与登记表。集外条目的内容改动不可能改变本次闭包——集外条目要么没被触及，要么其创建/删除会换 `archiveGeneration`；这也是把条目数写进指纹的原因。增量失效（E10）留待后续：现在是"变了就整体作废重取"，不是"只重扫受影响的条目"。

### 13.12 段内索引引用：`[hellparty] → etc/hellparty.etc →` 怪物与 AI（2026-10-17，任务 #21）

§13.9 留的那个缺口是本轮对象：**值的出口既不是路径、也不是 registry 行，而是"某条目某 section 内的记录"**。现有三种 Target（entry / registry / asset）表达不了，闭包因此整块漏掉深渊怪物组。

| 量 | 值 |

### 13.14 反向可达性、改动影响面与孤儿检测（2026-10-17，任务 #24＝E11/E12/E14）

一个反向索引回答三个问题：**谁引用它**（E11）、**改/删它会波及哪些种子**（E12）、**归档里有什么没人引用**（E14）。三者共用同一份数据，所以一次实现三个功能。

**为什么不需要数据库**：实测全归档建索引 **13.68 s**（20 并发，715,537 条目），索引本体估算 **40 MB**（`BytesEstimate`：每条链接 12 字节 + 每个被引用条目一个 map 桶）。进程堆此刻 507 MB，但那主要是归档自己的分块缓存（解码 432 MB），**不能拿它当索引体积汇报**——所以估算单独成函数。

**数据结构与语义**
- `Incoming{From, Name, Kind}`：`Name` 是内 interned 的边 id 或 `registry:<relation>`；**引用值不存**，需要时重读来源条目（`Explain`）。这是把 4.3M 引用压到几十 MB 的关键，而不是少存信息。
- `Kind` 四档：`edge`（被声明边解析到）/ `asset`（只被客户端资产边指到）/ `registry`（登记表行）/ `list`（它自己就是登记表）。**后两档是 E14 的否决条件**：登记过的 `.mob` 没有任何脚本引用也必须随包发布；`.lst` 是客户端按名字加载的根，把登记表列成孤儿是假警报。
- 建索引时对 **(to, from, edge, kind) 去重**：原始链接 1,987,350 → 去重后 1,309,362（**省 34.1%**），覆盖 514,916 个条目。重复的"同一来源经同一边指向同一目标"是一次事实，不是多次。
- `Ancestors(target, maxDepth)` 给传递祖先与跳数；`Impact(changed, seeds)` 与调用方的种子集求交，回答"这次改动动了我哪几个预设"。

**顺带补的能力**：`resolveAsset` 现在会尝试把资产路径落到归档条目上（多条同名则不猜）。资产引用仍然**不被闭包跟随**（`Ref.Followable` 的语义不变），但"只有资产指向这里"从此可测——否则 E14 无法区分"活内容"和"只是没进文本闭包"。

**实测（86 版，判据全绿）**

```
对偶性：3 个种子（副本 grakkarak.dgn 223 / hell_38142 434 / hell_amonhigh 337 条目）
        闭包每条边都能在入边表找到；入边表里来自闭包内的边级链接也都在正向闭包 reachable
        ——两个方向逐条核对，任一方向漂移即测试失败
#21 链的反向可用性：etc/hellparty.etc 入边 114（其中 109 来自文件名含 hell 的图），
        传递祖先按跳数 = {1:114, 2:85}（第二跳是引用这些图的副本）
E14：孤儿（无入边且无登记）= 200,621 条目，占全档 28.0%
        .ani 118,569 / .equ 21,616 / .til 10,883 / .als 8,454 / .act 6,729 / .ptl 5,122
登记条目被判成孤儿的数量 = 0（这条是硬约束，测试直接断言）
```

**一个被测量推翻的猜测（必须记下来）**：我原以为 28% 孤儿主要是 `%s` 动态模板造成的假警报（毕竟有 313,286 条动态资产引用）。抽样 3,040 个孤儿去匹配 642 个可用模板（先剔除 3 个 `%s` 这类字面量为空的**退化模板**——否则"100% 匹配"是自证的废话）：**只有 17 个（0.6%）能被模板解释**。所以孤儿集的主体不是模板，而是（a）真正的遗留/未使用内容与（b）尚未声明的引用类。把 E14 直接叫"死内容检测"会高估，需要再做一次交叉表：孤儿 × 未声明候选类 × missing 引用。已记入任务 **#25**。

**测试**：`reverse_test.go` 4 条合成（正向⊆反向且反向⊆正向、传递祖先与正向可达互证、深度语义 1/2 跳、Impact 与种子集求交、孤儿必须排除登记项与登记表本体）；`reverse_real_test.go` 1 条真实归档守卫（24 s，含上述全部数字）。

### 13.15 孤儿归因：28% 里到底有多少是死内容（2026-10-17，任务 #25）

§13.14 报出孤儿 200,621 条目（全档 28.0%）却不回答"其中多少真是死的"。`AttributeOrphans`（`internal/extraction/orphan.go`）用同一批扫描数据把集合拆成四档，优先级从上到下：

| 档 | 判据 | 86 实测 |
|---|---|---|
| 未声明边的受害者 | 某条 path 形候选能解析到它（补边即可消除） | **6,650（3.3%）** |
| 动态模板可解释 | 某个 `%s`/`%d`/`*` 模板按归档自己的解析规则能命中它 | **24,448（12.2%）** |
| 被提到但解析失败 | 有未解析引用（missing/歧义）的 TargetPath 就是它 | **682（0.3%）** |
| 无人引用 | 以上都不是 | **168,841（84.2%）** |

只有最后一档可以叫"无人引用内容"，占全档 **23.6%**。按扩展名看：`.ani` 未声明边 4,888 + 模板 24,445 + 无人引用 89,236；`.equ` 21,616、`.til` 10,494、`.als` 8,454、`.act` 5,819、`.qst` 4,356、`.map` 4,205、`.stk` 3,761、`.key` 3,229 全部落在最后一档。`AssetOnly`（只被客户端资产指到）= **0**，因为 86 的归档里没有与那些 `.img` 值同名且唯一的条目——资产指向的是 NPK，不是 PVF 条目。

**两次自我纠正，都得记下来**（第一次给出的"模板只能解释 0.6%"是错的，错在两个静默失效的 bug）：
1. **匹配器一开始恒返回 0**。原因是排序键与二分查找键不一致：排序用 `FullPath` 原样、查找用小写归一化路径。`sort.Search` 落在无关位置后，`!HasPrefix` 立刻 break ⇒ 什么都不匹配，但**没有任何报错**。教训：一个"结果为 0"的过滤器必须单独测，不能只测整体流程。
2. **模板是相对值，孤儿路径是全路径**。`templat%s.ani` 与 `passiveobject/obj/templated.ani` 段数不同，永不匹配。补了 `dynamicPatterns(fromPath, value)`：按归档自己的解析规则同时给出"来源条目目录相对"和"根相对"两种形态。修完模板档从 65 跳到 24,448。
3. 另外两个真实缺陷也在同一轮暴露：`literalBounds` 把 `%s.ani` 的 `.` 当成格式字符吞掉，字面后缀变空（⇒ 后缀匹配永远失败）；退化模板（`%s` 这种字面量为空）若不按 `literalRunes ≥ 3` 剔除，会"解释"全部孤儿。

**成本与定位**：`-orphans` 全程约 2 分钟（建索引 13 s + 重扫 13 s + 模板配对 4.15 亿次比较）。这是**离线工具**，不进提取路径，也不暴露给 UI；不变式（各档合计 = 孤儿总数、已解释项不得出现在"无人引用"样例里、匹配器与归一化的行为）由 `orphan_test.go` 合成用例守住。真档数字是手工跑出来的记录，不作为常驻测试（太慢），下版本要复核时直接跑 `edge-bench -orphans`。

**下一步的含义**：3.3% 的未声明边受害者是给 #23 的下一轮指路的（补哪类边能立刻减少孤儿）；84.2% 的"无人引用"要再切一刀才有产品价值——按"是否被任何预设的种子可达"和"路径是否属于活动/赛季内容目录"分层，否则它只是一堆文件名。

### 13.16 跨版本图 diff：条目、内容与引用三层可比（2026-10-17，任务 #26＝E15）

**先普查（结论：既有能力只到"路径/内容"，引用层是空的）**：`services/archive_diff_compare.go:51 archiveDiffComparePhases(before, after)` 已经能吃两个 Archive 实例做路径/内容对比；`internal/version.Repository` 只吃同一归档的提交历史，不能跨文件；`pvf.TokenComparisonCompatible` 只用于内容哈希兼容判定；`docs/MOD.md` 明确写"依赖补齐…**不补齐任意脚本、sprite、sounds、npk 资源**"。所以"同一份声明在两个归档里各自解析出什么"这件事，仓库里此前无人做过。多 Scanner / 多 Archive 并存没有障碍：`Scanner`/`RegistrySet` 各绑一个归档，`LoadCatalog` 每次新建，无全局单例。

**核心语义纠正：载荷字节跨归档不可比。** 脚本载荷把字符串存成**字符串池槽位**，槽位是每份归档自己分配的，于是两个方向都会出错：
- 内容相同 ⇒ 字节可能不同（实测 86 vs 客户端：`PoolRenumbered=6`）；
- **字节相同 ⇒ 内容也可能不同**（合成用例里两份归档的载荷都是 `03 24 00 00 00 06 32 00 00 00`，解析出来却是 `Tiles/Ground.TIL` 与 `tiles/other.til`）。
所以 `sameContent` 一律按 **token 值序列**（TokenType/Section/Value）判等，字节只用来区分"真相同"与"池重排"。这条是本轮唯一改变结论的设计修正——第一版按 `RawBytes` 比较，会把 74,808 条里 6 条误判，且反过来完全漏判"字节巧合"。

**API（`internal/extraction/graph_diff.go`）**
- `CompareEntries(left, right, workers)`：**分片按左档索引**（只是为了并行下输出确定），**匹配按路径**——每条走 `right.Find(left.FullPath(index))`，右侧未命中的用位图收进"只在对照"（左遍已经知道匹配到的右侧下标，省一次全量 `Find`）。所以"只在某侧 N 条"是真实的文件集合差，**不是索引错位**；#41 复盘时我把"按索引分片"读成了"按索引配对"，因此写错过结论，见 §16.10 的方法学第 2 条。两侧恒等式 `Same+Changed+OnlyX == TotalX` 由测试断言。

### 13.17 MOD 最小分发包：必带集、借宿主与破坏性引用（2026-10-17，任务 #27＝E13）

**要解决的问题是普查里那条 E13 缺口**：现有导出依赖补齐（`services/export_dependencies.go`）按设计只补文字表、表号映射与 `.lst` 行，**不补脚本、不补精灵、不补 npk**。所以一个改了 `.aic` 动作的 MOD 作者，看不到"我这个包还缺哪些文件"，也看不到"我把某个 `.act` 删了，但基线里还有 5 个文件在引用它"。这两件事在参考工具里靠人工经验，在这个仓库里此前没有出口。

**引擎**：`internal/extraction/modset.go`，`PlanPackage(baseline, mod, modScanner, baselineScanner, DiffVerdicts, PackageOptions)`。四个口径都是有意选定的：

| 输出口径 | 定义 | 为什么不并入别家 |
|---|---|---|
| `Carry` 必带集 | 改动/新增 ∪ 在 **MOD 自己**里可解析的传递依赖 | 从基线取依赖会把宿主版本的文件塞进包里，包就成了伪全量；卸载时删不干净 |
| `SatisfiedByBaseline` | MOD 解析不出、基线能解析的引用（带引用方与边 id） | 这是一条**兼容性声明**："本 MOD 需要宿主 PVF 至少有这些"。补进包=越权，静默丢掉=撒谎，只有列出来是对的 |
| `Unresolvable` | 两边都缺 | 真坏引用，与版本无关 |
| `BrokenReferences` | MOD 保留了引用方却删了被引用项 | 需要跑一次**基线全档反向扫描**，所以是 opt-in；它是"应用后哪些宿主文件会悬空"的清单，不是要打包的东西 |

护栏两个：`Scope`（只计划某子树）与 `MaxCarry`（上限，防一次误操作的全档改动直接索要整个游戏）。`ByCategory`/`ExtensionTotals`/`Bytes` 走的是 §15 已有的类别投影，所以预览勾选 UI 将来无需新数据。**上限命中必须可见（顺手补的第三类静默丢失）**。`Closure` 原先在 `MaxEntries` 处直接 `break`，返回的闭包形状与完整闭包毫无区别——"被截断的包"读起来就是"这个包只需要这些"。这与 §13 开头两条静默丢弃是同一个失败签名。现在 `Closure.Truncated/Dropped` 与 `PackagePlan.CarryTruncated/Dropped` 都会置位，CLI 直接打警告。`Options.MaxEntries` 此前**一条测试都没有**，本次补上（`TestClosureCapReportsWhatItDropped`：未设上限不得标记；命中上限必须标记并报出未展开数；截断不能凭空造出可达条目）。

**计划要能变成包**：`Selection` 新增 `Paths`（显式白名单），`PackagePlan` 新增 `Closure`，`Plan` 新增 `UnlistedPaths`（点名了但闭包里没有的路径）。有了这三样，E13 的输出直接喂给现有导出器（原文本 + `_registries` 片段 + manifest），不需要碰 `services`：


### 13.18 补边第二波：工单换成"包体报表"，并顺手补上解析阶梯缺档（2026-10-17，任务 #29）

**工单来源换轨**。#23 那批边是从**全归档缺口队列**取 top 类补的；本轮改成从 §13.17 那次真实打包的 `VerifyPlan` 报表取（30,342 文件的包报出 332 条 `missing-edge` / 37 类）。理由：缺口队列回答"哪里还没声明"，包体报表回答"**发这个包会缺哪些文件**"——后者才是用户会撞上的东西，而且它自带 `(引用方扩展名, section, 目标扩展名)` 三元组，正好是写 `Edge` 需要的键。CLI 侧把违规聚合键从"section"改成"引用方扩展名 + section + 目标扩展名 ×次数 + 一条可核对样例"。

**新增：按边实测审计**（`Aggregator.EdgeStats` + `edge-bench -all -edges N`）。原先只有 `ByEdge`＝**解析条数**，一条永远解析不到 0 的边和一个从不出现的边长得一模一样。现在每条边给出 `值 / 解析 / 缺失 / 歧义 / 解析率`，并且每个 (边, 状态) 额外留一条**字典序最小**的样例值（并行可复现，沿用 #23 的"样例取最小而非首个"约定）。第一轮审计就抓到两条 0.000 的既有错声明。

**审计抓到的是解析器的问题，不是数据的问题**——这是本轮最大的收获：

1. **`resolveDeclared` 把引用方目录丢了**。计数前缀记录（`walkCountPrefixed`）走 `resolveDeclared`，而它调 `resolveRelative("", value)`；非记录路径走 `eval`，用的是 `resolveRelative(fullPath, value)`。同一个引用值，**声明成边之后反而解不出来**（未声明时 `resolveCandidate` 又能解出——包体那 332 条违规就是这么来的）。修：把 `result.Path` 传进去。安全验证：127 条边逐条对账，**解析数下降的边 = 0**。
2. **解析阶梯缺"类别根"这一档**。PVF 有一类值既不相对引用方、也不相对归档根，而是相对**目标类别的根目录**：`town/alfhlyra.twn` 的 `[area]` 写 `Alfhlyra/Alfhlyra.map`，实指 `map/alfhlyra/alfhlyra.map`；`map/alfhlyra/(f)gate_alfh.map` 的 `[import script]` 写 `Common/(F)Gate_Seria.map`，实指 `map/common/(f)gate_seria.map`。两级实测都 miss（0/217、0/72）。落地为**声明式** `target.roots`（新增，带目录合法性校验，拒绝 `..` 与绝对路径），并且**排在 owner-relative 与归档根之后**才试——所以它只在"今天本来就解不出"的地方生效，是纯增益，不可能把已解析的改成不解析。修完实测：`twn.area` **217/217 = 1.000**、`map.importScript` **72/72 = 1.000**。
3. **`twn.area` 原来的记录宽度是错的**。它曾声明 `width:3 refOffsets:[1]`，而 `[area]` 的真实形状是 `路径 [类型]` 交替并夹着 `[minimap rect]` / `[normal]` 块标签，取第 2 列取到的全是标签。改为不定宽、由 `looksLikeArchiveEntry` 把关（与 `obj/stk [string data]` 同一口径）。顺带：宽度 lint 的白名单因此过期一条，lint 自己把这条过期项报了出来（**lint 的自校验在起作用**，12 → 11）。

### 13.19 留案重审：一次被实测按住的错误修复，和 `roots` 的第二种形态（2026-10-17，任务 #30）

§13.18 只重审了两条 0.000 边。本轮把剩下的都过一遍：166 条边逐条看解析率与样例，加 #23 那 4 个按"整体不在 86"放弃的类。

**先记录一次被推翻的假设**（这条比新增的边更值钱）。看到 `obj.stringData` 0.696、`ptl.object` 0.838、`obj.particleFile` 0.864 的缺失样例全是 `../../../PassiveObject/Common/Particle/FireExplosionParticle1.ptl` 这种形态，第一反应是"相对路径跳出了归档根，所以要加一档：把多余的 `../` 夹掉再按类别根找"。实测 715,537 条目里带 `../` 的值：

```
.act|base ani   63,834 条 → 现阶梯已解 63,284、跳出归档根只有 1 条、夹掉 ../ 命中 0、夹掉+类别根命中 0
.ptl|object     14,690 条 → 现阶梯已解 11,969、跳出根 0 条、夹掉 ../ 命中 0
.obj|string data   406 条 → 现阶梯已解   389、跳出根 0 条、夹掉 ../ 命中 0
```

**"夹掉 `../`"这一档在 86 上收益是 0**，那 3,000 多条缺失是拼出来确实不存在的条目（内容问题，判 missing 本来就是对的）。如果只看样例就动手，解析阶梯里会多一条永远不该存在、 yet 会改变未来归档行为的档。

**`roots` 需要第二种形态**。重审 `.key [particle filename]`（#23 判 0.000）：值的形态是 `key/dummy.ptl`，而 `.key` 文件自己就住在 `…/角色名/key/` 里 —— owner-relative 得到 `…/key/key/dummy.ptl`（错），归档根得到 `key/dummy.ptl`（错），**只有 owner 的父目录对**：`…/角色名/key/dummy.ptl`，实测 **772/773**。静态目录表达不了它，所以 `roots` 扩成两种：以 `../` 开头＝相对引用方往上若干层，其余＝归档内静态目录。校验允许前导的 `../` 串，但**中间的 `..` 一律拒绝**（`key/../..` 这种仍然报错），解析端再兜一次：拼完仍以 `../` 开头的候选直接丢弃。

### 13.21 E4 的种子形态：ID 档补上，名称档如实标缺（2026-10-17）

E4 写的是"种子（ID/路径/名称/当前打开文件）"，而 `Prepare` 里只有一行 `archive.Find(seed)` ——**只有路径真的能用**。P5 面板做完后这个缺口就从"文档措辞"变成了"用户看得见的功能缺失"：MOD 作者手上常常是表行号，不是文件路径。

**实现**：`internal/extraction/seed.go` 的 `ResolveSeed(archive, registers, seed)`，三档，按能否确定为边界：

| 形态 | 例 | 规则 |
|---|---|---|
| 条目路径 | `map/forest/a.map` | 原样 `Archive.Find`（现状） |
| 关系名:ID | `怪物:10021`、`map:1` | 左边必须**匹配到已声明的关系名**才当表查询，所以含冒号的路径不会被误判；命中即返回，未命中把 registry 的原因（无此 ID / 注册目标条目不存在）原样说出 |
| 纯 ID | `10021` | **只在恰好一个关系认领时接受**。多个关系命中 → 报错并列出候选 + 给出可直接改写的写法 |

**为什么纯 ID 要这样拦：实测过**。抽样 660 个真实 ID 逐一到所有关系里查：**唯一归属 101 条（15.3%）、歧义 559 条（84.7%）、查不到 0**。样例：`10014` 同时属于 `map、宠物、物品、被动对象、装备`。也就是说"猜一个"在真实归档上有 84.7% 的概率凭空造出一条用户没要的依赖。所以 UI 里**不推荐**纯 ID 写法（placeholder 只写"条目路径，或 关系名:ID"，并在提示里给出这组数字），解析侧则明确拒绝并教用户怎么写。

**名称档没做，这里如实标缺**。名称→条目需要给 `.mob`/`.aic` 等条目的 `[name]` section 建一张反向索引（86 有 71.5 万条目），而"谁会在提取时用名称当种子"这个消费者还没确认。按本项目"没有消费者就不建结构"的既有决定（§14.1 持久层退役同因），不做半吊子：E4 的这一档**仍未实现**，不是遗漏而是明确取舍。

**服务层**：`Prepare` 的失败种子信息从"种子不存在：<路径>"升级为"种子无法解析：<原因>"（带上 registry 判定的细节）。`TestExtractionServiceAcceptsIDSeeds` 钉住两件事：`map:1` 与 `map/forest/a.map` 必须给出**同一份闭包**（计数完全一致），以及无法解析的种子必须报错而不是换回一个空计划。

**面板顺带补的两处**（属于 §13.20 的欠账）：手输种子框（回车或"加入"才生效，逐字符重取闭包没有意义）；选项变化改为 **300ms 防抖**——原先每敲一个数字（条目上限）都会重走整次闭包，大集合上是几百毫秒到几秒，且这些请求全部串行排队。

**一次自己制造又当场抓到的事故，值得记**：用 python 脚本给前端文件打补丁时，把 `\n` 写成了真换行（正则 `/[\n,;]+/` 断成两行）、又把 `export function` 放进 setup 函数体内（语法错误）。同一类转义问题这一轮在文档上也出现过一次。结论：**改源码用 Edit 工具，不要用生成脚本**；脚本只在"批量同构改写且立即全量校验"时才划算，而这次两处都是单点小改。发现方式是 vue-tsc/oxc 直接报解析失败，不是靠肉眼。

**测试**：合成 3 条（三档形态 + 歧义拒绝 + 无法解析的解释）、真实归档 2 条（36 条 ID 种子与登记表原路径双向对上；660 条归属抽样把 15.3%/84.7% 钉成日志数字）、服务层等价性 1 条、前端 13 条（含手输合并去重与"连续改选项只重取一次"）。

### 13.22 落点改为原生目录对话框（2026-10-17）

上一版面板让用户**手输导出目录绝对路径**——这不是设计，是我图省事：服务层当时只暴露 `Execute(id, dir)`，前端就只好要一个文本框。而应用里所有"写到哪儿"的选择都走原生对话框（`ExportService.ExecuteDialog` / `ExecuteSelectionDialog`、`EditorService.ExportFilesDialog`、`VersionService.ExportCommitFilesDialog`）。手输的实际后果是写错一个盘符就得到一次被拒绝的写入，而不是被拦住。

**做法**：服务层新增 `ExtractionService.ExecuteDialog(id)`，三点是有意的：

1. **先验计划再弹框**。`executablePlan(id)` 在对话框之前判过期/未知 id，直接返回 `ErrExtractionStale`。顺序反过来就是让用户选完目录才告诉他"预览已过期"，等于骗他操作了一遍。守卫有专门用例（三种坏 id + `Release` 之后的正当 id 都要拒绝）。
2. **返回完整 `*ExtractionResult` 而不是路径字符串**。"181 个文件 / 0.55 MiB / 6 个登记表片段"才是让用户确认提取真发生了的信息；本仓库对话框惯例返回 string，这里破例是权衡后的选择，不是疏忽。
3. **顺带删掉两处死状态**：`outputDir`（被对话框取代）与 `result`（赋值完立刻关闭面板、无人读取）。前端不再自己传路径，也就没有"前端算出一个服务端会拒绝的目录"这类错误面。

**测试**：Go 侧 `TestExtractionDialogRefusesStalePlan`；前端 13 条里新增一条最容易写错的行为——**在目录对话框里取消，既不能结束会话也不能报错**（`ExecuteDialog` 取消返回 null，面板保持打开、预览仍可执行）。

**一条环境事实**：`wails3 generate bindings` 把 29 个 bindings 文件的行尾从 CRLF 写成 LF（内容不变）。本机 `core.autocrlf=true` 下这类改动在 `git diff` 里看不见，却会占满 `git status`，把真正的两处改动埋掉。已按 `git diff --ignore-cr-at-eol --name-only` 区分后还原，只保留 `services/index.ts`、`services/models.ts` 两处实质变化。**重生成 bindings 之后要顺手做这一步**，否则审查者无法分辨哪些是新生成的内容。

### 13.23 MOD 导出接上引用闭包补齐（2026-10-17，任务 #28）

`IncludeDependencies` 这个开关原先只做一件事：`addExportDependenciesLocked` 补**文字表、表号映射与 `.lst` 行**，`docs/MOD.md` 明写它**不覆盖脚本 / sprite / npk**。于是"改了 `.obj` 的 MOD 导出时没带上它引用的 `.ani`"这件事，在应用里没有任何一层会提醒——§13.17 的 E13 引擎算得出来，但只有开发 CLI 看得见。这次把它接进主链路。

**做法**：`services/export_dependencies.go` 新增 `addExportReferenceClosureLocked(source, pkg, writer)`，在 `Prepare` 的 `Mode == "mod" && IncludeDependencies` 分支里、表补齐之后运行：以包内 `ReplaceFile` 条目为种子走 `Scanner.Closure`，把"被引用却没在包里"的条目按同一套 writer 规则补进来（`.lst`/`.str` 仍走 merge 语义，不整份覆盖）。预览新增 `referenceDependencies` 字段，导出面板摘要行显示"另按引用闭包补入 N 个文件"。

**三条边界是它能进主链路的前提**（不是保守，是这三处一旦省略就会出错）：

| 边界 | 处理 | 为什么 |
|---|---|---|
| 提交快照导出（`source.snapshot != nil`） | **跳过补齐并在警告里说明** | 扫描器只能按当前归档解析；拿历史提交的内容去补，会补进那个提交里根本不存在的文件 |
| 补齐数量 | 上限 20,000 条，命中即警告"还有 N 条未展开" | 每个补入条目都带整份内容在内存里；不设上限的一次误选可能索要整个游戏（§13.17 的截断可见性纪律） |
| merge 条目（表 delta） | 不当种子 | 它不是一份脚本，扫它会按包外语义去解析登记行 |

**悬空目标必须指名**。同一趟顺手产出第二条信息：**包内引用有 M 个目标在本归档里不存在**（最多 3 条 `来源 [section] → 目标` 样例）。这是补齐唯一救不了的失败模式，也是"我的包发出去会不会引用到没有的文件"最直接的回答。逐条目重扫而非读 `closure.Unresolved`，因为后者不带"这条引用来自哪个文件"（与 `PlanPackage` 同一个理由）；扫描结果有缓存，这一步不重新解析文本。

**真实归档实测**（`dungeon/act1/grakkarak.dgn` 单一种子，格式取第一个可写描述符）：

```
包内条目 1 → 224   文字表依赖 1   引用闭包补入 222（其中 .ani 162 条）
Prepare 1.27 s（含一次扫描器预热 ≈0.5 s；第二次起走缓存）
警告 1 条：包内引用有 4 个目标在本归档里不存在
  例 tauguard.mob [normal] → monster/tau/ai/Event.ai
```

**scanner 缓存归一**（这次接线的真正前置工作）：抽出 `services/scanner_cache.go` —— `scannerCache.forArchive` + `contentWitness` + `relationSpecsOf`，提取服务与 MOD 导出共用同一份键规则（归档指针 + generation + 规则引擎身份 + 登记表/段索引内容指纹）。两处各自实现缓存键，迟早有一处会漂，这与 §14.1 的依赖方向结论同源。锁序固定为「服务锁在外、`core.mu` 在内」，并把 `witnessSet` 改成不持服务锁去问缓存——否则 `cache.mu → s.mu` 与 `s.mu → cache.mu` 会反向。规则重载后扫描器必须换实例这条，测试从"读私有字段"改成"两次 `scannerFor` 比较返回指针"，不再依赖结构体内部布局。

**一个由全量测试才暴露的死锁**：第一版缓存自己在内部取 `core.mu.RLock()` 读内容指纹，而 `Prepare` 函数体**已经**持着这把读锁。Go 的递归读锁在没有排队写者时能过，所以单跑用例会绿；一旦有写者排队（应用里 autosave 与索引重建就是写者）就永久阻塞——表现是整包 `go test ./services/` 卡到超时，堆栈停在 `scanner_cache.go` 的 `RLock`。改法是**指纹由调用方按姿势传入**：`coreWitness(c)`（自己加读锁，提取服务用）与 `unlockedWitness()`（调用方已持锁，导出用），代际与规则引擎身份直接读字段。教训：**读锁不是"多一个读者无所谓"**，任何被持锁方调用的工具函数都不能自己再加读锁，且这条只能用"排队写者 + 看门狗"的用例钉住，普通用例钉不住。

**测试**：合成 3 条（`.obj → .ani` 由引用闭包补上、同目录未被引用的 `.ani` 不进包、开关关掉一个都不补；悬空目标必须指名 `gone.ani`；**持 `core.mu` 读锁时补齐不得自锁**）+ 真实归档 1 条（把上面那组数字钉成断言：补入 ≥100、耗时预算 30 s、结果里必须有 `.ani`）。既有的 `TestExportSelectionDirectAndModDependencies` 等导出用例全绿，说明这层没有改变表补齐的既有结果。

**那条锁用例第一次报的是 `got 0`，而问题在测试自己**：手写 `modpkg.Package` 时没带 `Metadata.Name`，`Extend110Writer.Validate` 第一件事就是查包名 ⇒ 每一条补入都被拒、只写进日志和 `diagnostics.skipped`，返回值仍是 0，看起来完全像"闭包什么都没解出来"。修法是补上名字，并额外断言 `diagnostics.skipped == 0`——**"没跑到"和"跑了但被静默跳过"必须可区分**，这是 §13.15 那条"任何结果为 0 的过滤器都要单独有一条用例"的纪律又一次命中，只不过这次的过滤器是写入器校验。

### 13.24 E10 派生缓存增量失效：先测量再决定，结论是不做（2026-10-17）

| 只重建最大的一张登记表（`equipment/equipment.lst`） | **53 ms** |
| 登记表 + 段索引的内容指纹（31 条目 / 2.08 MB） | 2 ms |
| 已预热扫描器上单副本闭包 | 14 ms / 223 条目 |

**触发条件决定了收益的落点**：`scannerCache` 的键只对**那 31 个登记表与段索引文件**敏感（`sc.watched`），其余一切就地编辑**根本不重建扫描器**——被改的脚本内容会在下一次闭包遍历时重新读取（`Scanner` 内部没有按条目的扫描结果缓存，只有登记表与段索引表有，而两者都在指纹集合里）。所以增量失效能省的上限是 `415 − 53 ≈ 362 ms`，且**只出现在"用户改了登记表行"这一种少见动作之后的一次提取**；常见路径（改 `.str`/`.obj`/`.ani`）本来就只付 14 ms 那一级。

**代价**：要在扫描器里新增"按关系驱逐"的机制，于是失效判定出现**第二个真相源**（一层是指纹整体作废，一层是内部子缓存各自驱逐），与 §13.10 三层键和 §14.1 依赖方向的结论同源冲突；`Scanner` 还要多暴露可变接口。

**判定：不做**。判据是事先写的"收益要落在常见路径且 ≥100 ms"，实测两处都不满足（少见路径、且省的是几十到几百毫秒的一次性预热）。留了重开条件：若将来出现"批量改登记表 + 反复提取"的真实工作流，或预热在端到端耗时里的占比明显上升，再按本节的数字复议。

顺带用一条测试钉住本节的前提（"就地编辑会不会被缓存吃掉"）：`TestExportModClosureFollowsAnEditedReference`——给 `door.obj` 新增一条 `[use animation]` 引用后再 `Prepare`，新目标必须出现在包里。这条同时确认产品编辑路径（`EditorService`）会推动导出预览的校验信号；直接调 `Archive.SetText` 绕过服务层则不会，而那不是产品路径。

## 十五、导出内容分类与预览勾选（2026-10-16 补，用户提出）

这是模型层的缺失，不是导出层的补丁。E9 早就写了 `Prepare→Preview→Execute` 三段契约，但 **Plan 里只有"整个闭包"一种粒度**，没有类别维度 ⇒ UI 只能退化成"全导 / 不导"。补上类别维度之后，E9 的 `Preview{tree,counts,warnings}` 与 `ExecuteSelection` 才有可勾选的对象。

### 15.1 分类是投影，不是新数据结构

`Node.Via` 已经带着"把这个条目拉进来的那条引用"（`Ref.EdgeID / Ref.Kind / TargetPath`），所以类别**当场可算**，无需给节点加持久字段、也无需重跑扫描。实测代价为零（投影在已算好的 277 节点上做）。

1. 边上显式声明的 `category`（可选，供语义特殊的边覆盖，如"称号动画"要归 UI 而非动画）；
2. registry 边的 `relation` 名（`被动对象 / 怪物 / APC / 物品 / 任务` ⇒ 直接就是业务类别）；
3. 目标条目扩展名映射表（下表）；
4. 归 `其他`，并进缺口报表——**"其他"非空就是分类表要补的信号**，与 §4.3 三态可见性同一条设计原则。

| 大类 | 成员（实测 86 目标扩展名 / relation） | 六种子实测（283 条目 / 0.21 MiB） |
|---|---|---|
| 场景骨架 | `.dgn` `.map` `.twn` `.tbl` | 6（但 `.tbl` 两个文件占 124 KiB，是全量体积的 58%） |

### 15.2 勾选语义（决策 8：默认保闭包）

`Selection = 类别集合 × 深度上限 × 三态过滤`。导出集分三段：

- **主集**：命中勾选类别的节点；
- **补链集（ancestor）**：主集节点到最近种子的路径上的祖先——不补则目录里出现"有子无父"，树不可导航；
- **外联集（outgoing）**：主集与补链集的 **resolved 出边目标中未命中勾选类别**者。它们仍要落盘（否则判据 1 的封闭性被破坏，而封闭性正是本次联调的立身判据），但落到 `_external/<大类>/` 并在报表单列，`manifest.json` 里标 `autoCompleted: true`。

**必须如实告诉用户的代价（实测）**：默认语义下取消勾选**不会减少落盘总量**，只改变归属目录与报表分组。原因是补入是**传递**的：86 实测依赖树里 `.ani` 之间有 **155 条**互相引用，另有 场景→动画 1、怪物→动画 16、战斗→动画 6、物件→动画 3 条入边。所以取消"动画与贴图"这 1 类，26 个动画会被直接拖入，再沿动画内部的 155 条边把剩下的也拖进来——**184 个文件一个都少不了**，只是从主目录挪进 `_external/动画与贴图/`。上表"283 条目里动画占 184"这个占比就是取消勾选不减量的规模证明。要真正减小总量，只有两条路：① 显式 `strict: true`（严格只导勾选项，manifest 标 `partial`，报表逐条列出指向未导出条目的**悬空引用**）；② 把"动画与贴图"改成 `asset` 型边（引用记录、永不落盘）——后者是**语义修正**而非选项，第一版已定 asset 层不做，所以 `strict` 模式必须存在，否则"只要数据包"这个真实诉求无法达成。预览界面要同时显示这两个数字（主集 / 补入 / 悬空），让用户在知情的前提下选。

### 15.3 目录布局（`layout`，三选一）

| 值 | 形态 | 适用 |
|---|---|---|
| `mirror`（默认） | 镜像归档原路径 `pvf/<archive path>` | 回填、对比、与原包结构对齐 |
| `category` | 每大类一个子目录（"按类别分开导出"） | 交付、人工浏览、按类别打包 |
| `seed` | 每种子一棵子树 | 多个互不相干请求一次跑完 |

`category`/`seed` 布局下同名条目必须靠已有的 `sanitizeExportName`/`safeExportPath` 防覆盖（`internal/extraction/export.go:17` 的常量块旁边扩展，不新造路径逻辑）。

### 15.4 预览一次算完，亚秒级

实测：6 种子 → 283 条目闭包 859 ms（含 basename 索引一次性构建）、`missing 89 / unknown 15`、0.21 MiB。预览**不落盘**，直接在 `Closure` 上做投影即可，无需新算法。每大类显示：文件数(去重) / **字节** / 引用数 / 将被补入数 / 未解析数 / 3 条示例路径——**文件数与字节必须同时给**，否则用户无法理解"勾掉动画只减 31% 体积"这类反直觉结论。快捷预设：**全选**、**只要数据（排除动画与贴图，自动切 strict）**、**按种子一层**、**含未解析项**。

### 15.5 新增两条可证伪判据

自动补入若不可验证，就等于"偷偷多写文件"。所以：

- **判据 4（补入后封闭性）**：`Verify` 跑在"主集 ∪ 补链 ∪ 外联"上必须为 0 违反；`strict` 模式下违反数必须**等于** manifest 里的悬空引用数（不许出现第三种情况）。
- **判据 5（补入可复原）**：所有 `autoCompleted` 条目必须全部位于 `_external/`，且从 `manifest.json` 单文件即可复原完整集合——报表不重复、不放漏。

|---|---|---|
| `internal/extraction/edges/extract-edges.json` | 新增顶层 `categories`（大类显示名、排序、扩展名/relation 归属）；边可选 `category` | 配置，逐版本迭代 |

## 十六、装备提取规格：知识库 × 反编译代码 × 真实归档三对齐（2026-10-17 补）

目标是把"给一件 `.equ`，该带走哪些东西"定成**可复核的数据**，不是照抄 pvfsimple 的代码。三方各自负责什么：知识库（`E:\00\knowledge`）给段的语义与 ID 空间；反编译代码给**产物形态**（用户要求的对齐目标：哪些文件、哪些 `.lst` 行、套装块、img 清单）；真实归档（86 版）给"这个段的值到底能不能解析"。

### 16.1 一条必须先说的度量学结论：解析率要按数值量级分档读

普查 `.equ`/`.stk` 各段时，"命中率"这个指标本身会骗人——登记表密到 0..N，**任何小数都能撞上 ID**。活样本：`[inventory limit]` 全是 `3000`，在 被动对象 上命中 0.99；`[avatar type select]` 有 20 万个 0/1，在 物品 上 1.000。**所以声明的判据换成三条**：① 按量级分档（`0-1 / 2-99 / 100-9999 / 1e4-1e5 / >=1e5`）逐档看；② 与登记表在**各档的行数**对照（见 16.2 开头控制表）——`装备` 119,515 行、`物品` 162,544 行，它们在小数值档报 1.00 不证明任何东西；而 `apd` 在 `1e4-1e5` 档只有 37 行（该档有 9 万个可能取值），`[appendage]` 6,861 值全部命中才是证据；③ **定性优先于定量**：`[appendage group]` 实测 90/90 = 1.00 但知识库说它是效果分组号，这种"高分且语义相反"以知识库为准、不声明。

**img 从哪来（知识库 + 样本一致）**：`[icon]`、`[field image]`、`[icon mark]`、`[extra icon]` 都是 **两列：`.img` 路径 + 帧号**；`.ani` 里是 `[IMAGE]` 的 `.img` + 帧号（`[IMAGE POS]` 是坐标，**不是图片**）；穿戴外观走 `[equipment ani script]`→`.lay`→`.ani`→`[IMAGE]` 这条链。**所以不需要参考工具那张 925 条硬编码表**（`EquAniFanHuiImgPath`，还绑定特定客户端版本）——沿声明式边走就能拿到模型 img，这是结构上的优势。`[image packs]` 在知识库与 `config/*.json` 里**零记载**（我们已有一条 asset 边 `equ.imagePacks`，1,568 值），语义待定，不得据此声称能列 NPK。

**img→NPK 只能靠扫目录，没有命名规则**：知识库对映射规则是**未记载**；参考工具也是"扫 ImagePacks2 → 解密每个 NPK 的 img 名表 → 精确字符串匹配"（`NpkFile.cs:528`、`Sqlite.cs:15-17` 的 `ImagePacks2(id,img全路径,img名称,npk文件名)`），且 `sprite/.+\.img` 之外的裸文件名一律落 `(未找到)`（`:451/548/589`），`%d%d.img` 展 01–09（`Dnf.cs:255-265`）。一个 NPK 装多张 img（KB 实测口径 1612 NPK / 80941 IMG 条目，键数≠条目数因含 `sprite/` 别名）。**推论**：资产产物必须依赖用户在设置里选好 NPK 目录，未选就明说"资产未解析（无目录）"；同名跨目录、模板 `%s`/`%04d`、大小写与别名命中一律记 `unknown`，**不得降格为 `missing`**（KB `client-compatibility-matrix-boundary-quick` 的硬规定）。

**不抄的缺陷**（都在反编译代码里查实）：礼包深层递归**无深度上限**且环检测只按 ID、路径每轮重复入表 ⇒ 成环空转；`[stackable type]` 的 switch **没有 default**，未知类型过筛后静默丢弃；段值正则**钉死制表符宽度**，宽度一变整段零命中；NPK 侧只认 `NeoplePack_Bill` 头（`NC$_image` 静默跳过）、不读版本/压缩标志 ⇒ 重写容器有损坏风险、写出不去重。本项目由闭包天然去重 + `MaxDepth`/`MaxEntries` + "未声明即入候选队列（不静默）" 避免前者，资产侧**只读不重写 NPK**（不做合并/删除，避免后一类风险）。

### 16.4.1 资产产物已落地（任务 #36，2026-10-17）：真实数据把推测变成事实

三点要记下来：

1. **没有命名规则可依赖，只能扫目录**——这与参考工具一致（它也是解密 NPK 名表后精确匹配）。因此没选 NPK 目录时产物必须明说"只有路径、没有归属"，不能装作这批图片不存在（已写成断言）。顺带修正一处口径：知识库记的"1612 NPK / 80941 IMG"与本机实测的 4337/143,482 差数倍，那是不同客户端构建的目录，**引用知识库数字时要带上是哪份目录**。
2. **动态模板记 `unknown`，不降格 `missing`**（既有硬规定，这次由 `%d`/通配的 12 条真正走了一遍）。
3. 本次 50/50 命中是"86 归档 × S4A21 容器"这一对的结果，**不可外推成任何配对都命中**；换配对后差在哪，对照表会逐行显示。100.7 MiB 也说明"默认不拷"是对的——那是需要用户看一眼数字再决定的事。

### 16.5 预设的定义方式（沿用 E8 已定口径）

预设 = **起始节点集 + 允许边子集 + 深度**，不是新代码路径。装备预设草案：种子 = 选中的 `.equ`（或 `装备:ID`）；允许边 = 16.2 表里 `equ.*`/`stk.*` 系 + 段内索引；深度不限但受 `MaxEntries` 约束；产物按 16.4 的五项组织，资产默认出"路径→NPK 归属"清单，复制 NPK 与解码 PNG 作为可选档。

### 16.6 本轮暴露出的两个引擎缺口（老实记下来，不硬塞）

1. **段值门控缺失**：`[int data]` 的列形随 `[stackable type]` 的**值**变化（百宝箱 / 怪物卡 / 配方 / 宠物蛋 四种），而 `Edge.Under` 只匹配祖先**段名**。要么加"按兄弟段取值路由"的声明能力，要么这四类永远只能留案。当前倾向：先做前三类最常见的（百宝箱、怪物卡、宠物蛋），因为它们的形状有官方注释样本背书。
2. **一条记录里两种目标**：`.equ [passive object]` 同一条 6 列记录既有 registry ID 又有 `.ptl` 路径，现有 schema 一条边只有一种 `target.kind`。要覆盖它需要"记录内多列分别指向不同目标"的表达能力——**在没有明确消费者之前不做**（同 §14.1 否决持久层的理由）。
3. ~~**套装索引还差一条边**~~ → **已由任务 #37 解决**：新增第三种 target 形态 `section-table`（块内"键列→值列"直查，不需要 kind 路由，也不需要动共享的 `config/lists.json`）。三条边落地并全档实测：`.equ [part set index]` 84,541 值 → 84,523 解析 = **1.000**；`[effect part set index]` 2,629 → 0.994；`[reference effect part set index]` 994 → 0.984；全档解析再 **+88,114**，既有边零下降。**表文件本身刻意不跟随**——跟进去等于把 2,415 个套装全拉进一件装备的包，`TestSectionTableEdgeResolvesOneRowOfATable` 把这条钉住了。块的切分按结构（标签 token 或换段即边界）而不是固定宽度：套装块的部件行数本身可变，按宽度切会漂。

### 16.7 预设层落地（任务 #35，2026-10-17）

预设按 E8 的口径实现为**数据而不是新代码路径**：`internal/extraction/edges/extract-presets.json`（embed 自持，与边目录同一处理方式），每条预设只有 `id / name / description / seedHint / categories`。首发四个预设：副本、装备、道具、礼包（任务 #38 扩到七条，见 §16.8）。

**预设明确不做的事**（是设计约束，不是偷懒）：不裁剪闭包、不排除边、不改遍历深度。理由用实测说：给装备预设加"只走装备族边"的白名单，会把礼盒真需要的 `.ani`、宠物链 `.cre`、突破材料 `.stk` 一起裁掉；而闭包本来就是引用驱动的——一件布甲的闭包就是 1 个条目（图标 + 自身），不需要过滤来保持干净。所以预设只承担两件事：**给类别默认值**（面板上看得见地改变勾选）和**给种子写法与说明**（`seedHint` 就是 `装备:46700` 这种可直接粘贴的形态；这类 ID 从 #38 起由真实归档测试钉住，不许凭空写，见 §16.8.1）。

**契约**（都有测试）：`Presets()` 在服务侧对类别表校验，预设引用不存在的类别是**加载失败**而不是安静选出空集合；`request.preset` 认不出时报"未知的提取预设"而不是退回无预设；`preview.preset` 回显生效预设；显式 `categories` 优先。`TestExtractionPresetsApplyDefaultsButNeverNarrowClosure` 断言带不带预设 `closureCount` 必须相等，并复验"取消勾选不减落盘总量"（少掉的主集项以 `_external/` 补回）。

面板新增预设下拉（首位"不用预设"），选中后选项行下显示一句说明，例如装备预设写着"…图片要落在 NPK 里，产物带资源对照表"。前端两条 store 用例：预设只改类别默认并按选择送进请求；`Presets()` 取不到时面板照常工作、不把错误甩在用户脸上。

**各预设实测的闭包形状**（说明文案按这个写，不承诺做不到的事）：礼包 `christmas_inboostersm.stk` 46 条目（`.ani` 30 / `.equ` 10 / `.cre` 5 / `.stk` 1）；宠物蛋 6 条目；普通消耗品 `stackable/gold.stk` 1 条目——**闭包小是正确结果**，所以道具预设的说明里写明"多数只有图标与自身文本是正常的"，免得用户以为漏了东西。

### 16.11 110 版缺口归因与 8 条边：差点把 13 万条真依赖记成资产（任务 #42，2026-10-18）

§16.10 留了一句没验过的话——"110 的 378 万 path 形缺口大概是因为边目录不认识 `contents/` 这套新组织"。实测归因后，这句**只对了一半，而且危险的一半在别处**。

**先纠正报表词汇（这是本轮真正的工具修复）**：`-edges` 那列原本印 `EdgeStat.Unknown` 却标成"歧义"，而 `EdgeStat` 里根本没有同名歧义的计数。Unknown 实际混着三种成因完全不同的判决：

| 成因 | note 前缀 | 该怎么处置 |
|---|---|---|
| 同名多目标 | `同名条目 N 个` | 不能猜：加 `roots` 或收窄值规则 |
| 动态模板 | `动态路径，无法静态判定` | 声明没错，客户端才知道 |
| **解析到条目但扩展名不在 expectExt 内** | `解析到条目但扩展名不在…` | **边声明过窄**（#40 的 `obj.stringData` 就是这么发现的） |

现在 `cmd/edge-bench` 印成 `未知=N（同名 a / 动态 d / 其他 o）`，差额显式留在"其他"里；`Aggregator` 新增 `perEdgeAmbiguous` / `perEdgeDynamic` 两个计数器，按 note 前缀归类，**认不出的成因一律不进拆档**（不变式 `同名+动态 ≤ 未知`，由 `aggregate_test.go` 两条用例守住，其中一条专门测"表文件本身不跟随"这种陌生 note 不得混进任何一列）。自校验：86 的 `ani.frameImage` 拆出 动态 313,235，与 §13.13 当年记的"313,235 转 unknown，全是模板"**逐位相同**。

**归因结果**（110 全档，同一份目录）：

**A.5 遗留待查**：`registry-unresolved=6` 未逐条归因（疑为 `[ai character]` 记录宽度 4 的假设值与实际不符，或 `[special passive object]` 全量 t=0 粗上界带来的假 ID）；`[special passive object]` 的真实变宽规则尚未实现，spike 用的是"所有整数全送解析"的上界，**会高估该 section 的解析成本**，但也给出了安全上限。
