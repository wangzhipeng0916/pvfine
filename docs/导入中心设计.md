## 一、定位与三条硬边界

导入中心不是"又一个导入弹窗"。它补的是提取中心一直缺的那一半：**提取出来的东西没有回灌的路**。`docs/提取中心设计.md:1637` 把产物定义成「实体 + lst 行 + img 列表 + 可选 NPK 容器」，这份产物本身就是按"可导入"设计的，只是读的那一侧从未写过。

三条不可动摇的边界：

| # | 边界 | 为什么 |
|---|---|---|
| **B1** | **与提取的文本形态同源**：同一对编解码器、同一路径语义、同一类型来源。`form=raw` 的条目（`.ani`/`.til` 等二进制）**不在 v1 范围**，在预览中列出并标记，绝不写入 | 文本侧本来就是为回灌设计的（`internal/extraction/form_export_test.go:14-17` 的原话：这是 extract → edit → 源码导入能往返的前提）。二进制侧若走 raw，脚本 token 里存的是**归档全局字符串池绝对偏移**（`internal/pvf/stringpool.go:229-248`），跨归档写入会静默错位——v1 先不碰这一半 |
| **B2** | **预览零副作用**。`Open` / `Edit` 只在克隆体上工作，活归档一个字节都不动；只有 `Execute` 会写 | 预览一旦有副作用，"取消"就不再是取消。所有判定（含登记表索引）都在 `a.CloneForBatch()` 上完成，丢弃克隆体即可完全回退 |
| **B3** | **写不了的要在预览里说**，不能等到保存才报 | `CanChangeStructure=false` 只在 `validateWrite()` 报错（`internal/pvf/format.go:99-107`），110 页表容量同理（`paged110.go:267-269`）。用户在预览阶段就要知道"这批东西导完存不下去" |

## 二、契约：`manifest.json`

**现状：只写不读。** 写入点唯一（`internal/extraction/export.go:563`），全仓库无任何读取方。

这是把两边串起来的唯一正确接口，也是本设计最省力的一处：提取侧已经把导入需要的东西都写好了。

| 字段 | 导入侧用途 |
|---|---|
| `Files[].path` | **目标归档路径**（不是磁盘相对路径） |
| `Files[].dest` | 磁盘上的落点，**相对 `manifest.subdir`**（默认 `pvf`），不是相对导出根 |
| `Files[].form` | `text` 可导入 / `raw` 不支持（B1） |
| `Files[].category`、`autoCompleted` | 预览分组与默认勾选 |
| `Selection.RegistryFragments[]` | 涉及哪几张表、各多少行、多少缺失 |
| `Selection.Mode` | `closed` / `strict`，判断这份产物是否完整 |
| `ClientVersion`、`Format`、`CatalogEdges` | 跨版本导入的警告依据 |
| `Assets[]` | img → NPK 归属（P3 用） |

### 需要新增的字段

```go
// internal/extraction/export.go, ExportedFile
DataType int32 `json:"dataType,omitempty"`

// internal/extraction/export.go, Manifest
Subdir string `json:"subdir,omitempty"`
```

`Subdir` 记录载荷目录（默认 `pvf`）。`Dest` 是相对它的路径：`Export` 走的是
`resolveUnder(root, subdir, dest)`。不记录这个字段，CLI 换一个目录名导出就再也
找不到任何文件；旧 manifest 没有它，按默认值补。

**兼容**：旧包没有 `DataType` → `0`，导入侧必须走扩展名推断（`SetDataType` 传 0 会直接报错）。

读取器放在 `internal/extraction/manifest.go`（与写侧同包，共用 `Manifest` 结构体），不新建包——一旦两边各写一份结构体，加字段时必然漂移。

## 三、阶段链

```
选源 → 解析成候选 → 计划（可编辑） → 冻结 → 执行 → 可选：加入文件集
```

`计划` 与 `冻结` 全程只读（B2）。冻结令牌沿用 Mod 导入那套已验证的机制（`services/mod_import.go:233-236`）：归档指针 + `batchRevision` + `versionLoadID` + `versionHead.ID` + 创建时间。

> ⚠️ **`archiveGeneration` 不是内容令牌**：它只在索引安装时递增（`services/core.go:383/644/750`），纯内容编辑只递增 `batchRevision`。把 `archiveGeneration` 写进冻结条件会给人"内容已冻结"的错觉。

### 3.1 文本格式对齐（与提取同源）

「导入 text」不是"只接受看起来像文本的文件"，而是**与提取的 `form=text` 逐项对齐**。四个维度里两个已经天然对齐，两个必须补：

| 维度 | 提取侧 | 导入侧 | 现状 |
|---|---|---|---|
| **内容编解码** | `Payload` → `a.Text(index)`（`internal/extraction/export.go:160-174`）：反编译成带缩进的脚本文本，无 `.txt` 后缀 | `readImportFiles` 校验 UTF-8 → `a.SetText` / `a.AddFileText`（`services/import.go:518-522`、`537-546`）→ 重新编码成 token 流 | ✅ **同一对编解码器**，现有 `ImportModeText` 就是它 |
| **编码** | UTF-8、无 BOM | UTF-8、允许可选 BOM（strip，`import.go:522`）、非 UTF-8 直接拒绝 | ✅ 已对齐 |
| **路径** | 写在 `pvf/<原归档路径>`，路径记在 `manifest.Files[].path` | 按「选中的目录名 + 相对路径」推导（`import.go:417-436`），**目录会再套一层** | ❌ **必须改成读 manifest** |
| **类型** | `ContentForm` 只看 `DataType`（`export.go:136-145`），与扩展名无关 | `importDataType` 只看扩展名：`.str`/`.nut` → Unicode，其余 → Script（`import.go:528-534`） | ❌ **判据不同，`DataType` 必须进 manifest** |

这张表就是 P0 的全部工作量：内容格式不用写解码器，**要补的是路径与类型**。

一个具体的错位例子：某个 `TypeUnicode` 条目如果扩展名不是 `.str`/`.nut`，提取侧按"文本"写出，导入侧却按扩展名判成 `TypeScript` —— `SetText` 会把它重新编码成脚本 token 流，文件内容看着一样，类型变了，客户端行为可能就不一样。`DataType` 字段是这条的唯一解。

### 3.2 输入源

| 档 | v1 是否支持 | 说明 |
|---|---|---|
| **提取包**（含 `manifest.json`） | ✅ 主路径 | 路径、form、dataType 全部来自 manifest |
| **普通目录 / 文件** | ✅ 降级 | 无 manifest → 全局 text、路径按「目录名 + 相对路径」，与现有 `ImportFiles` 语义一致 |
| **MOD 包** | ❌ 不进导入中心 | 已有 `ModImportService` 带 plan/TTL/令牌，重写一遍必然漂移；入口保持在导入弹窗的「Mod」页签 |

### 3.3 文件冲突三态

| 态 | 判定 | 默认 |
|---|---|---|
| `new` | 归档里没有该路径 | 勾选，写 |
| `overwrite` | 有，内容不同 | **不勾选**，需显式勾 |
| `unchanged` | 有，内容相同 | 跳过（不写，避免制造假变更） |

**`unchanged` 的判定域必须与写盘形态一致**：

- 磁盘上是导出时 `a.Text(index)` 的结果（`internal/extraction/export.go:160-174`），**走用户渲染规则**；
- 因此比较对象是 `a.Text(index)`，不是 `CanonicalText`。用规范文本比会**永远判成 overwrite**（规范文本刻意忽略渲染覆盖，`internal/pvf/file.go:134-136`），"无变化"这一档就形同虚设；
- `DataType` 不同 → 强制 `overwrite`（`SetDataType` 是真实变更）。

UI 上该态标注为「文本相同（与渲染规则相关）」，不写成斩钉截铁的「无变化」。

### 3.4 `.lst` 不走文件通道

`.lst` 是 `TypeScript`、`form=text`，按普通文件写会走 `SetText` **替换整张表**（`internal/pvf/file.go:160-178`，它把整段文本重新编码成载荷），目标表里用户没看见的行全部消失。

**P0 直接拒绝把 `.lst` 当普通文件写入**，全部转交 §四 的登记表环节。这条是硬约束，不做"确认后放行"。

## 四、登记表

### 4.1 索引 schema

```go
// internal/importing
type ListIndex struct {
    ListPath  string          // 归档内真实路径
    ListIndex int32
    ByID      map[string]Row  // id -> 该行
    ByRowPath map[string][]string // 规范化行路径 -> 持有它的 ids
}

type Row struct {
    ID        string
    RawPath   string // 表里的写法（可能相对表目录，也可能归档根相对）
    FileIndex int32  // 解析到的归档文件索引；解析不到 = -1
}
```

三条必须遵守的规则：

1. **索引建在「文件已应用之后的 clone」上。** 本次新增文件的登记行，只有在文件进入克隆体之后才能被 `findListTargetInArchive` 解析到；否则一律判 `new`，产生重复行。
2. **`ByID` 必须同时存书写路径与解析结果（可为 -1）。** 只存索引会让"ID 存在但指向缺失文件"退化成"ID 不存在"，于是被当成 `new` 再追加一条同 ID 行。
3. **`ByRowPath` 是主索引，`FileIndex` 是辅助。** 计划阶段候选文件还没进归档；陈旧行也解析不到文件。只按文件索引建键两头都漏。

表定位一律用 `Archive.FindList`（`internal/pvf/archive.go:519-531`），它已经覆盖 90/110 两套布局，不要自己拼 `list/`。

### 4.2 判定（不分实体行 / 引用行）

```
按 ID 查
 ├ 命中且同路径 → registered   跳过（幂等，不是错误）
 └ 命中且异路径 → id-taken     冲突
按路径查（规范化后）
 ├ 已被别的 ID 登记 → duplicate 冲突
 ├ 空              → new       写
 └ 解析不到任何文件 → dangling  只报告，不写
表不存在            → no-table  整表报错，不新建
```

**为什么不按「实体行 / 引用行」分**：

- `internal/extraction/fragments.go:152-158` 明确写着「一行同时是被引用与实体自身时不重复写：它已经在前一段里了」——按段分类必然漏掉"被别的导出文件按 ID 引用的实体"，而怪物召唤、套装互引里这是常态；
- 更根本的是语义：**实体性是导入时属性**（取决于用户这次勾了哪些文件），而段标记编码的是**导出时**属性。用户取消勾选一个文件，标记就错了；
- 按"目标侧能否解析"判定与两者都无关，且天然正确：能解析的写、解析不到的不写。

**附带结论：不需要给 `_registries/*.lst.fragment` 加任何格式标记。** 解析器用 `pvf.ParseListText`（`internal/pvf/list_text.go:11-56`，本就容忍注释与空行）把行全读进来即可，旧包新包一视同仁。

### 4.3 写回

| 步骤 | 做法 | 依据 |
|---|---|---|
| 行路径 | **按目标布局重算**：`listEntryPath(targetListPath, targetArchivePath)` | `services/list_registration.go:428-439`。照抄 fragment 里的写法会在 90↔110 之间写出解析不到的死行 |
| 写入 | `Archive.SetListPairs`（按 ID upsert，未涉及行按原 token 逐字节保留） | `internal/pvf/metadata.go:279-342`，保真测试 `metadata_test.go:230-266` |
| 删旧行 | `Archive.RemoveListIDs`（`remove-old` 消解用） | `metadata.go:349` |
| indexhash | `RequiresIndexHash` 时对改过的表调 `SetIndexHashEntriesForListIDs` | `internal/pvf/indexhash.go:200-220`。配套文件不存在必须**硬错**，不静默跳过 |
| 禁止 | 不用 `mergeModTable` | `services/mod_import.go:240-313` 整表重渲染，语义不对 |

`SetListPairs` 本身是**静默 upsert**（同 ID 直接换 path）。因此**冲突消解必须发生在调用它之前**，不能让它替用户决定。

v1 **不做 `reassign`（自动换新 ID）**：换号会让导入后的实体 ID 与提取时脱钩，后续无法对照，且是最容易点错的一项。`nextListID`（`list_registration.go:441-461`）保留给后续版本。

### 4.4 结果必须报「仍缺失」

`Execute` 的返回值里必须有一等公民计数：

> 「N 个引用 ID 在目标表中仍然缺失」

少了它，UI 会把残缺读成成功——这正是本项目最贵的失败模式。

## 五、NPK 精简（P3）

### 5.1 它解决什么

`copyAssetContainers`（`services/extraction.go:657-700`）是**整包拷贝**：一个副本闭包只要 3 张图，但命中的容器可能有 200 MB，这 200 MB 全进产物。归档内的 `_external` 补链逻辑管不到 NPK。

### 5.2 流程

```
包内 npk/ 容器 ──逐条目──> 目标 ImagePacks2 是否已有同名 img
                              ├ 路径相同 + 成员字节相同 → identical  默认精简掉
                              └ 路径相同 + 成员字节不同 → different  默认保留并标红
目标目录：只读，一个字节都不改
输出：写到一个全新的输出目录
```

`different` 必须单独成一档：路径相同但内容不同**不是重复，是覆盖**。少这一档，用户做的换皮会被"去重"静默删掉，删的还是他自己改的那份。

### 5.3 实现要点

| 点 | 做法 | 依据 |
|---|---|---|
| 成员字节 | **原样拷贝**，只重算 offset | 不需要 IMG 编码、不需要 DXT、不需要 zlib |
| 名字 | 复用原始 256 字节密文 | `npk.go:109-112` 已把密文读进来；新增 `Entry.RawName [256]byte`（`json:"-"`），彻底避开 EUC-KR 往返与 `TrimSpace` 丢空格（`npk.go:119-131`） |
| 容器头 | 20B + 264×N 条目表 + 成员数据，成员起点 4 字节对齐 | `npk.go:73-117` |
| 输出 | 新目录，`.part` + `os.Rename` | 范式见 `services/extraction.go:680-696` |
| 空容器 | 成员被精简光则不写文件 | — |
| 索引刷新 | 写 NPK 必然改 size/mtime，持久化索引自动过期重建 | `services/image_service.go:737-740` |

### 5.4 安全边界（缺一不可）

- 目标目录未配置 / 索引未就绪 → **P3 禁用并说明原因**，不能"假定无重复"保留全部，也不能"假定有"就删；
- 不能只用持久化索引判断"哪个容器有同名 img"：索引按路径去重只留第一个容器（`image_service.go:350-358`），会漏掉多容器同名；
- 包内容器损坏 / 非 `NeoplePack_Bill` → 跳过并计数，不得计入覆盖率；
- 解码名要过与 `internal/mod/model.go:74-115`（`ValidatePath`）同级的路径校验（分隔符、`..`、尾点尾空格、控制字符、Windows 保留名），防止写出时穿越；
- 成员 offset 必须 ≥ 源头部结束位置（`npk.Open` 只查边界，`npk.go:99-104`）；
- 同一 offset/size 的别名成员只复制一次并复用新 offset，否则体积翻倍；
- 重算后逐条校验 int32 偏移上限（单容器 ≤ 2 GiB）；
- 包内两个容器同名 → 检测，不互相覆盖；
- preview → apply 之间源容器若被改动（size/mtime 变化）→ 拒绝执行。

## 六、事务与版本

### 6.1 应用序列

```
archiveTasks.begin()
  c.mu.Lock()
    1. 校验冻结令牌 + TTL
    2. ensureVersionReadyLocked()                  ← 漏了会没有版本库却继续走
    3. 记 repo / loadID / head
    4. stage := a.CloneForBatch()
    5. batchRevision++（预约）                      ← 回锁二次校验的基准
  c.mu.Unlock()
    6. 在 stage 上应用：文件 → 登记表 → indexhash（带进度与取消）
    7. prepareArchiveDerivedIndexes(stage)          ← 锁外
  c.mu.Lock()
    8. archive==a && batchRevision==revision+1 && repo/loadID/head 全等，否则 ErrBatchPlanStale
    9. after 快照（路径并集见 6.2）
   10. 安装：incremental SQLite 走 rebuildArchiveIndexesLocked，否则 installPreparedArchiveIndexesLocked
   11. recordVersionMutationLocked("导入中心", before, after)
   12. MutationsSince(0) / ClearMutations
   13. invalidateRegistrationIndexesLocked(c)      ← 改过表就必须调
   14. refreshRegistrationEditorTextLocked(...)    ← 表正在编辑器里打开时，不调会被旧文本覆盖回去
  c.mu.Unlock()
   15. scheduleArchiveMutations
   16. emit archive:changed / archive:advanced-search-stale / emitVersionState
```

**「无变更早退」必须放在第 6 步之后**：文件全同但表需要写的批次，不能因为文件没变化就当成空批次返回。

### 6.2 undo 必须覆盖表

`recordVersionMutationLocked` 靠 before/after 两份快照的并集判变更（`services/version.go:407-423`）。快照路径必须是：

```
files ∪ 被写的 .lst ∪ 被写的 _indexhash.etc
```

漏掉表路径的后果不是报错，是**撤销只还原文件、表里新行留着**。`RegisterFileToList` 就是这么做的（`list_registration.go:199-227`），照抄。

### 6.3 预览期就要拦的三件事

1. `Archive.WriteCapabilities().CanChangeStructure == false` → 拒绝新增文件/行（否则保存时才报）；
2. 110 页表容量不足 → 拒绝（`paged110.go:267-269`）；
3. 上限：200,000 文件 / 512 MiB，命中要**显式出现在结果里**，不静默截断（沿用 `Closure.Truncated` 的诚实做法，`internal/extraction/closure.go:70-76`）。

## 七、UI

`ImportCenterModal.vue`，三段式，与提取中心对称：

```
源（选包 / 选目录）
   ↓
计划 ┌─ 页签1 实体文件  勾选 / 改目标路径 / 状态筛选
     ├─ 页签2 登记表    逐行状态 + 冲突选择 + 缺失计数
     └─ 页签3 图片/NPK  重复项 + 精简选择（P3）
   ↓ 冻结
执行 → 结果摘要（写入 N / 覆盖 N / 跳过 N / 仍缺失引用 N）
   ↓
可选：加入文件集
```

**编辑的边界**：只做**计划级编辑**（勾选、改目标路径、选冲突策略），不做内容级编辑——内容要改去编辑器。

大包必须服务端分页/聚合，不能沿用现有预览的 500 条封顶（`services/import.go:20-21`）。

### 文件集联动

默认**新建批次文件集**（如 `导入 · 2026-10-20 · 装备`），可在下拉改成"加入当前集"。

理由：导入一批实体后，用户接下来多半要逐个调这些文件；塞进当前集会污染已有上下文。技术上 `addEntries` 已按规范化路径去重并返回 `{added, skipped}`（`frontend/src/stores/fileSets.ts:117`），只需在成功后补一次元数据。

## 八、非目标

| 不做 | 原因 |
|---|---|
| raw 形态导入（v1） | 二进制条目暂不处理，扩展规则见 §十一 |
| 删除归档条目 | 导入管线现在没有删除路径；删除是不可逆语义，应留在归档操作里 |
| 自动换新 ID（`reassign`） | 会与提取时的 ID 脱钩 |
| 改动目标 NPK 容器 | 明确不做；P3 只写新容器 |
| 给 fragment 加格式标记 | §4.2 已证明不需要 |
| MOD 包走导入中心 | 已有 `ModImportService` |
| MCP 暴露 | 再加一套 plan 机制会变成第三套语义。若将来暴露，必须绑定 workspaceId + revision |

## 十一、附录：二进制条目将来怎么接

v1 不处理 `form=raw`，但提取产物里它们占多数（一个副本包 252 条目中约 192 条是 `.ani`/`.til`）。将来要接时，判据不能是"raw 一律拒绝"，也不能是"raw 一律允许"，而要按 **数据类型** 分：

| `dataType` | `form` | 处理 | 理由 |
|---|---|---|---|
| 1 `TypeScript` | text | ✅ 导入（v1 已做） | 有编码器，可往返 |
| 3 `TypeUnicode` | text | ✅ 导入（v1 已做） | 有编码器，可往返 |
| **1 `TypeScript`** | **raw** | ❌ 拒绝 | token 里是归档全局字符串池**绝对偏移**（`internal/pvf/stringpool.go:229-248`），换归档即错位且不报错 |
| 3 `TypeUnicode` | raw | ✅ 可导入 | UTF-16LE 字节自包含，无池引用 |
| 其它（0/2/5/6/7…） | raw | ✅ 可导入 | 二进制载荷自包含（`.ani` 能脱离归档被 `ani.DecodeBinary` 单独解析即是证据），原样搬运安全 |

要注意 `.ani` 的特殊之处：它有文本解码器（`internal/pvf/file.go:127-129`），但**没有对应的编码器**，所以 `ContentForm` 只能给它 raw（`export.go:136-138` 的注释写明了这个理由）。要让它走文本，得先写 ANI 文本编码器——那是另一件事。

接入顺序：先在 `manifest.Files[].dataType` 就位之后（P0 已做），再把 §3.3 的三态扩展成 text/raw 两套比较；raw 二进制比 `RawBytes` 是逐字节精确比较，比 text 还简单。
